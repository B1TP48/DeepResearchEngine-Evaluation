# Precompute Feeds, Pool Connections, Defer Sharding

At roughly one million daily active users, a Twitter-like app does not need sharding or active-active multi-region writes on day one. It needs a connection pooler, read replicas, a cache, precomputed timelines, object storage for media, and asynchronous workers, all in one well-chosen region behind a CDN. The binding constraints are the single primary’s connection count and write amplification from counters and fan-out, not InnoDB’s data-size ceiling, which runs to a 64 TiB internal tablespace, though ext4 caps a file at 16 TiB ([MySQL 8.4 Reference Manual, InnoDB Limits](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html)). A read-heavy planning model of 40 requests per user per day gives about 40M requests/day, ~463 rps average and ~1,400–2,300 rps at a 3–5× peak; if 10% of users post once a day to 200 followers, that is ~20M timeline writes/day, ~231/s average. That load fits one large primary plus replicas and Redis, at roughly $11k–13k/month in a lean configuration. Sharding becomes mandatory when peak writes reach ~10–20k/s, roughly a 10× user base; multi-region writes become necessary only when latency or legal residency demands it. If “1M users/day” actually means 1M requests/day, the plan collapses to one managed MySQL instance, one cache, and a CDN; if it means 10M DAU, sharding and regional read paths move into the first year.

## One primary plus a pooler and replicas carries 1M DAU; the write path, not storage, sets the ceiling

The arithmetic is modest at this target. A 40-requests-per-user-per-day model gives ~463 rps average, while a 100M-reads/day model gives ~1,160 reads/s average and ~5,800/s at a 5× peak; an 85–95% cache hit rate leaves ~300–900 reads/s reaching the database, which one primary plus two replicas can absorb. Twitter’s 2013 workload ran ~300K timeline-read QPS against ~6K write QPS, a roughly 50:1 read/write shape, which is the right planning bias for a social feed ([High Scalability](http://highscalability.squarespace.com/blog/2013/7/8/the-architecture-twitter-uses-to-deal-with-150m-active-users.html)). Storage is also small: 2M tweets/day at 0.5–1 KB is 1–2 GB/day, or ~30–60 GB/month, plus ~50–160 GB/month of follow/like edges, so the database reaches low-single-digit TB in year one. Those per-user figures are planning assumptions, not sourced ratios, and must be replaced with the startup’s telemetry before purchase decisions.

The first wall is connections and write throughput. MySQL uses one thread per connection, its default `max_connections` is 151 in community documentation, and RDS derives the default from memory as `DBInstanceClassMemory/12582880`, giving 683 connections on an 8 GiB instance ([AWS Docs](https://docs.aws.amazon.com)). Thousands of application workers cannot each hold a server connection, so a pooler (ProxySQL, Vitess/PlanetScale pooling, or an equivalent) is a prerequisite rather than an optimisation. A single primary realistically sustains ~3,000–5,000 durable TPS, and practitioner guidance puts sharding at ~5,000–10,000 simple inserts/s at peak; a 4-core MySQL 5.7 benchmark was reported at ~500 TPS and ~10,000 QPS ([Tencent Cloud Developer](https://developer.cloud.tencent.cn); [LinkedIn post by Debabrata Nayak](https://www.linkedin.com)). No official MySQL document states a supported maximum TPS, so ~5k writes/s is a planning ceiling, not a specification.

The order of work follows from those limits: fix schema, indexes and N+1 queries; add a connection pooler; scale vertically and size the buffer pool; add read replicas for lag-tolerant reads; partition large tables only where foreign keys are absent; shard; then add CQRS read models. The first four steps are reversible in days, while sharding is a multi-quarter commitment: Etsy’s shard-management migration to Vitess took five years and ~2,500 pull requests, and its payments migration moved 23 tables and over 40 billion rows into 40 Vitess shards over Dec 2020–May 2022 ([InfoQ](https://www.infoq.com/news/2026/04/etsy-vitess-sharding/); [Etsy Engineering](https://www.etsy.com/il-en/codeascraft/scaling-etsy-payments-with-vitess-part-2--the-seamless-migration)). Vitess defines a shard as one MySQL primary plus many replicas, and supports split/merge and table moves without application downtime, but that machinery is worth adopting only when the single-primary ceiling is actually in sight ([Vitess, Sharding](https://vitess.io/docs/reference/features/sharding/)). MySQL partitioning is not a substitute: partitioned InnoDB tables cannot have foreign keys, and differing SQL modes between source and replica can cause partition distribution to diverge ([MySQL 8.4 Reference Manual, Partitioning Restrictions](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations.html)).

| Data class | Default store | Why | Scale caveat |
|---|---|---|---|
| Users, credentials, message-of-record | Sharded MySQL/Vitess, Aurora, or Spanner | Multi-row transactions, unique constraints, SQL operations | Spanner Standard is $0.90/node-hour, one node is three replicas, storage $0.30/GiB-month ([Google Cloud Spanner pricing](https://cloud.google.com/spanner/pricing)); Aurora claims ~5× MySQL throughput and 15 replicas but that is vendor marketing, not a sizing number ([Amazon Aurora MySQL Features](https://www.amazonaws.cn)) |
| Timelines, counters, rate-limit buckets | Redis; DynamoDB or ScyllaDB for durable high-write data | Single-key reads/writes, increment-friendly | DynamoDB still caps a partition at ~1,000 WCU and 3,000 RCU/s, so one hot key throttles ([AWS re:Post](https://repost.aws)); Cassandra QUORUM is 2 of 3 replicas ([DataStax docs](https://docs.datastax.com)) |
| Media bytes | S3/GCS plus CDN | InnoDB rows are capped at ~8,000 bytes for a 16 KB page, and blobs would consume buffer pool and backup bandwidth ([MySQL 8.4 Reference Manual, InnoDB Limits](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html)) | Serve renditions from CDN, never through app workers |
| Search | Postgres full-text first, then Elasticsearch/OpenSearch | 10–50 GB per shard and under 200M documents is Elastic’s guidance ([Elastic](https://www.elastic.co/search-labs/blog/elasticsearch-node-shard-size-best-practices)) | 100k posts/day at 300 B–1 KB is ~11–36 GB/year, so volume is not the driver; relevance features are |

Distributed SQL options differ mainly in cost shape and write scaling. CockroachDB publishes 1.68M tpmC at 140,000 warehouses with a 95% efficiency score and recommends 4 vCPU per node minimum, 4 GiB RAM per vCPU, and 32 vCPU as the OLTP sweet spot ([CockroachDB Benchmarking Overview](https://www.cockroachlabs.com); [CockroachDB Production Checklist](https://raw.githubusercontent.com)). TiDB’s own FAQ says insert TPS grows roughly 40% linearly within 10 nodes, while MySQL “is single-node write” and scales writes only by sharding; its sysbench run reports 246,386 QPS at 150 threads and 396,715 QPS at 600 threads ([pingcap/docs-cn FAQ](https://github.com); [TiDB docs](https://docs.tidb.io)). DynamoDB is the cheapest throughput option for single-key data at this volume—$0.6250 per million writes and $0.1250 per million reads, with 1 KB write units and 4 KB read units ([Amazon DynamoDB pricing](https://aws.amazon.com/dynamodb/pricing/on-demand/))—but it lacks multi-row ACID transactions and global unique indexes, which makes “email must be unique” awkward. Vendor benchmarks for Aurora, ScyllaDB and Redis are self-reported; ScyllaDB’s own test shows 196K ops/s versus Cassandra’s 56K, but that should not be used for sizing without a workload-specific test ([ScyllaDB](https://www.scylladb.com)). No sourced throughput or consistency finding for MongoDB was available, so it is not recommended on this evidence.

Caching is the main lever on the read path. Cache-aside in Redis with a per-key TTL and delete-on-write is the default for profiles, single posts and follower counts; Redis documents sub-5 ms p95 for cached entities and warns that an expiring popular key can send dozens of concurrent processes to the database, so a Lua-scripted mutex or probabilistic early refresh is required ([Redis, cache-aside](https://redis.io/docs/staging/DOC-6719/develop/use-cases/cache-aside/)). Moving from 90% to 95% hit rate halves origin load, because misses fall from 10% to 5% ([Fastly](https://www.fastly.com)); at 10,000 req/s, 90% still means 1,000 database misses/s, while 99% means 100/s ([cachee.ai](https://cachee.ai)). Plan on 85–95% for social reads and do not assume 99% outside static/media metadata. Counters need special handling: a single counter row is a serialization point, and on DynamoDB one counter key is capped at roughly 1,000 WCU/s ([Stack Overflow](https://stackoverflow.com)). Use Redis `INCR`/`HINCRBY` with a periodic batched flush, a sharded counter table (`counter_id, bucket 0..N-1, value`) read by SUM, or an event log with periodic aggregation; follower counts can tolerate seconds of staleness, but viral like counts need bucketing. At 0.1× scale, a plain `UPDATE ... SET count = count + 1` inside the transaction is fine; at 10×, counters must be asynchronous by design.

Database cost depends on the managed option. One writer plus two readers on db.r7g.2xlarge-class hardware is ~$2,100–2,400/month at $0.956/hour for RDS MySQL or $1.11/hour for Aurora, before storage and backups ([cloud-credits.org](https://cloud-credits.org); [Vantage](https://instances.vantage.com)). The same logical throughput on DynamoDB on-demand is roughly $300–500/month for ~500M writes and ~1.5B read units, but loses relational constraints; Spanner Standard starts at ~$657/month per node before storage. Third-party RDS price summaries disagree for db.r6g.xlarge—$0.450/hour, $0.518/hour and $0.520/hour appear across sources, with Multi-AZ roughly doubling to ~$759/month—so database cost should be re-quoted from the AWS calculator rather than taken from any single summary ([Vantage instances](https://instances.vantage.sh); [c3x.dev](https://c3x.dev); [wring.co](https://wring.co)). At 0.1×, a single 8 vCPU/64 GiB instance plus one replica is ample; at 10×, writes reach ~10–20k/s peak and a single primary is definitively out.

## Precompute ordinary timelines, but pull celebrity posts at read time

The follow graph is not the scaling bottleneck at 1M DAU, and it should not be a graph database. One million DAU at ~200 follows each is roughly 200M edges; at 16–24 bytes per edge that is ~4–15 GB, a graph that fits comfortably in a partitioned MySQL/Postgres schema and even in memory across a few nodes. Twitter built FlockDB as “a distributed graph database for storing adjacency lists” backed by off-the-shelf MySQL, explicitly not optimised for graph traversal; it stored edges as 64-bit integers with a 64-bit `position` used for sorting and paging, partitioned by node so each query hit one partition ([FlockDB blog](https://raw.githubusercontent.com/twitter-archive/flockdb/refs/heads/master/doc/blog.md)). At 2010 scale that graph held 13+ billion edges and sustained 20k writes/s and 100k reads/s ([flockdb README](https://github.com/zhangwei5095/flockdb)). Facebook’s TAO similarly keeps the graph in MySQL behind a graph-aware cache of objects and associations, orders association lists by time, and reports a billion reads and millions of writes per second from one deployment ([The Morning Paper: TAO](https://blog.acolyer.org/2015/05/19/tao-facebooks-distributed-data-store-for-the-social-graph/)). The absence of a head-to-head benchmark against graph databases is a real gap, but the architectural evidence points the same way: single-hop adjacency reads and set arithmetic are relational/index problems, while multi-hop suggestions belong in offline batch jobs. A practical interface is `is_following`, `followers(id, cursor, limit)`, `following`, `follow`, `unfollow`, plus a precomputed follower count; the graph store should stay a simple KV/relational service and timelines should consume follow/unfollow events.

The home timeline is where write and read costs trade off. Fan-out-on-write precomputes each follower’s timeline as post IDs, so a feed read is one range scan but a post costs O(followers) writes. Fan-out-on-read costs one write per post but O(followees) lookups per feed load. Twitter kept each home timeline in Redis capped at 800 entries and said “the text of the tweet is almost irrelevant to most of Twitter’s infrastructure” ([High Scalability](http://highscalability.squarespace.com/blog/2013/7/8/the-architecture-twitter-uses-to-deal-with-150m-active-users.html)). At Twitter scale the average fan-out was 403, 3,500 statuses/s implied ~1.4M timeline writes/s, and a 20M-follower post implied ~21.4M writes ([Red Planet Labs (archived)](https://web.archive.org/web/20241129114422/https://blog.redplanetlabs.com/2023/08/15/how-we-reduced-the-cost-of-building-twitter-at-twitter-scale-by-100x/)). At 1M DAU with 200 follows and 10% of users posting daily, push fan-out is ~20M timeline writes/day (~231/s average); at 20% posting it is ~463/s average; a 3–5× peak is ~0.7–2.3k/s. A single post from a 10M-follower account is 10M timeline writes, roughly 43× the entire daily base-case push volume, and cannot be done synchronously.

The defensible design is hybrid. Push to followers when the author is below a threshold—Red Planet chunks fan-out at 64k followers per iteration, re-queues the remainder, and completes a 20M-follower post in 312 iterations, about 3 minutes, while most users with fewer than 64k followers are delivered in one iteration. For authors above the threshold, write the post once to `user_posts:{author}` and merge it into each reader’s page at read time; with 200 followees and a handful of celebrities, that is one range scan plus a few “latest from author since cursor” lookups. Cap each inbox at 800 entries and expire it after 7–30 days or on inactivity, so memory tracks DAU rather than all registered users. IDs-only storage is ~12.8 KB per 800-entry timeline, or ~12.8 GB raw for 1M timelines (~25 GB with list overhead); caching full bodies would be 240 GB at 300 B/post or 800 GB at 1 KB, which is why timelines hold IDs and hydrate bodies from a KV/cache. Post storage itself is small: 100k posts/day at 300 B is ~30 MB/day, ~11 GB/year.

Keying should make the read path three round trips. Use a 64-bit time-ordered post ID (Snowflake-style; Instagram’s documented scheme embeds a logical shard number and uses a 41-bit millisecond timestamp plus a 10-bit sequence, capping one shard at 1,024 IDs/ms) ([GitHub patterns notes](https://github.com)). Store `post:{post_id}` as a hash/JSON of author, text, media refs and created_at; `user_posts:{user_id}` as a sorted set of the author’s own IDs; `home:{user_id}` as a sorted set trimmed to the newest 800; `followers:{id}` and `following:{id}` as adjacency sets paged by `position`; and `notif:{user_id}` separately so notification reads never scan the timeline. Read one page with `ZREVRANGEBYSCORE home:{uid}`, pipeline a multi-get of the 50 post bodies, and multi-get author objects—three round trips, O(log N + M) on the sorted set, typically under 50 ms. Offset pagination fails on feeds because inserts shift the window, counts are expensive, and deep offsets scan and discard rows; use an opaque cursor over `(score, post_id)` instead ([Contentful](https://www.contentful.com/fr/blog/cursor-based-pagination/)). Ranking should happen after candidate retrieval: pull 2–5× the page size of IDs, hydrate, score with a relevance model, then cut to N, as Twitter describes for its ranked timeline ([Ranking Tweets with TensorFlow](https://blog.tensorflow.org/2019/03/ranking-tweets-with-tensorflow.html)). Read-your-own-writes requires writing the author’s post synchronously into `home:{author}` and `user_posts:{author}` before the asynchronous fan-out completes; follower timelines can be eventually consistent within seconds or minutes.

Search and notifications are separate concerns. Search volume is tiny at this scale—100k posts/day at 300 B–1 KB is ~11–36 GB/year—so the choice should be driven by relevance features, not volume; start with Postgres full-text search, then move to a small Elasticsearch/OpenSearch cluster sized at 10–50 GB per shard and under 200M documents ([Elastic](https://www.elastic.co/search-labs/blog/elasticsearch-node-shard-size-best-practices)). Vector search is additive: pgvector’s HNSW and IVFFlat indexes are approximate, with recall below 100%, so semantic results should be a recall channel merged with keyword results, not the primary timeline path ([pgvector reference notes](https://raw.githubusercontent.com/damusix/skills/refs/heads/main/postgres/references/94-pgvector.md)). Notifications must not fan out per follower: FCM batches up to 500 messages per call, so a 1M-recipient broadcast is 2,000 API calls ([Firebase Cloud Messaging](https://firebase.google.cn/docs/cloud-messaging/send/admin-sdk?hl=en)). Push only mentions, replies and follows; use a capped in-app inbox and a digest for “new posts from people you follow” rather than pushing every post.

## Make the app tier stateless, queue the slow work, and keep the monolith modular

Statelessness means every request can be served by any instance because nothing that must survive the request lives in that instance’s memory or disk. Identity travels with the request as a signed JWT or an opaque session ID resolved against Redis; uploads go from browser to object storage via a presigned URL; background work goes to a queue; and every state-changing retry is protected by an idempotency key. The Twelve-Factor process model states that processes are stateless and share-nothing, with persistent data in a backing service ([The Twelve-Factor App](https://12factor.net/)). S3 presigned URLs grant time-limited upload access bounded by the creator’s permissions, can be set to expire in up to 7 days, and overwrite an existing object if the same key is reused—so upload keys must be unique per attempt and namespaced by user ID ([Uploading objects with presigned URLs (Amazon S3)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.md)). Stripe’s idempotency keys are client-generated, up to 255 characters, and must not contain sensitive data ([Stripe API: Idempotent requests](https://docs.stripe.com/api/idempotent_requests)). SQS standard queues are at-least-once and may deliver duplicates, so consumers must be idempotent; the visibility timeout controls how long a received message stays hidden ([Amazon SQS queue types](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-queue-types.html)). Kubernetes’ HPA excludes not-yet-ready Pods from the scale-up signal and assumes they consume 0% of the desired metric, which dampens scale-up exactly when a new fleet is warming ([Horizontal Pod Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)).

The default should be a modular monolith, not microservices. Shopify describes microservices as “touted as the end-all solution” but chose one codebase with enforced boundaries, one repository, one test and deployment pipeline, and a single shared database; every additional piece of infrastructure increases DevOps time and possible failure points ([Deconstructing the Monolith (Shopify Engineering)](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity)). Twilio Segment split into one microservice per destination, ended up with over one hundred destination types, “exploding complexity”, plummeting velocity, and three full-time engineers mostly keeping the system alive ([Goodbye Microservices (Twilio Segment)](https://www.twilio.com/en-us/blog/developers/best-practices/goodbye-microservices)). Prime Video’s serverless microservice version supported only ~5% of expected load, with S3 intermediate objects and Step Functions transitions driving cost; consolidating into one process removed the intermediate bucket and cut infrastructure cost by over 90% ([InfoQ](https://www.infoq.com/news/2023/05/prime-ec2-ecs-saves-costs/)). Extract only where the scaling curve, failure boundary or runtime genuinely differs: media transcoding, notification/fan-out workers, auth/token service, and possibly the feed read service once its read curve diverges sharply. A 5–15 person startup can realistically own 2–3 services plus the monolith, and every extracted boundary imposes the transactional outbox, idempotent consumers and ordering discipline that AWS’s outbox guidance describes ([Transactional outbox pattern (AWS Prescriptive Guidance)](https://docs.aws.eu//prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)).

The front door should be CDN → L7 load balancer/ingress → services. ALB is for HTTP/HTTPS with path/host routing, TLS and WAF attachment; NLB is for TCP/UDP, static IPs and source-IP preservation, and ALB defaults to round robin with least-outstanding-requests available ([Load Balancing (Amazon EKS best practices)](https://docs.aws.amazon.com/eks/latest/best-practices/load-balancing.html)). An API gateway is optional at this size; if used, its default account throttle is 10,000 RPS per region with a 5,000-request burst bucket, and some regions default to 2,500 RPS with a 1,250 burst—check that ceiling before launch ([Amazon API Gateway quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/limits.html)). Autoscale on requests-per-target or in-flight requests, with queue depth for workers, not CPU alone; the Kubernetes Metrics API exposes only CPU and memory by default, so request-rate metrics need a custom/external adapter ([Resource metrics pipeline](https://kubernetes.io/docs/tasks/debug/debug-cluster/resource-metrics-pipeline/)). HPA runs on a 15-second loop, ignores changes within a 10% tolerance, picks the largest desired replica count across metrics, and applies a 5-minute downscale stabilization window by default. Lambda’s default concurrency quota is 1,000 per region, with a 15-minute maximum duration and up to 10,240 MB per function ([Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.md)); KEDA’s SQS scaler computes replicas as messages divided by a `queueLength` target (default 5) and counts visible plus in-flight messages by default ([KEDA | AWS SQS Queue](https://keda.sh/docs/2.21/scalers/aws-sqs/)). For a small team, managed containers with serverless compute (ECS/Fargate-style) beat self-managed Kubernetes on operating burden; Fargate is positioned as serverless compute for containers on ECS and EKS ([Amazon ECS clusters (AWS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/clusters.html)).

Queues should sit between the request path and every piece of work that need not finish the request. Write the event in the same database transaction as the state change (transactional outbox), make every consumer idempotent, and give each queue its own retry policy, exponential backoff with jitter, and dead-letter queue with an alarm on depth and age. SQS standard queues provide unlimited throughput, at-least-once delivery, possible duplicates and best-effort ordering; FIFO queues provide strict ordering and up to 3,000 messages/s per API method when batching (300 API calls/s × batch of 10), or 30,000 TPS in high-throughput mode with relaxed ordering within message groups ([Amazon SQS queue types](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-queue-types.html)). Kafka provides total order only within a partition; a total order over a topic requires a single partition, which allows only one consumer per group ([Kafka documentation (introduction)](https://docs.apache.googlesource.com/kafka/docs/introduction.html)). NATS JetStream adds at-least-once delivery with replay, and RabbitMQ quorum queues are Raft-replicated FIFO queues useful for poison-message handling ([JetStream (NATS documentation)](https://beta-docs.nats.io/); [Quorum Queues (RabbitMQ)](https://www.rabbitmq.com/docs/quorum-queues)). Segment’s own account is the cautionary example: retryable errors (HTTP 500s, rate limits, timeouts) were retried, non-retryable errors (invalid credentials, missing fields) were not, but putting retried and fresh messages in one queue caused head-of-line blocking ([Goodbye Microservices (Twilio Segment)](https://www.twilio.com/en-us/blog/developers/best-practices/goodbye-microservices)). Use SQS-style task queues for fan-out, notifications and media processing; use a partitioned log only when analytics or replay is a product requirement.

Media should never transit the application tier. The client asks the API for a presigned PUT, uploads bytes directly to object storage, an object-created event enqueues a transcode/thumbnail job, and the resulting renditions are immutable, content-addressed objects served through a CDN with long cache lifetimes. AWS Elemental MediaConvert is a file-based transcoding service driven by jobs, queues, templates and presets, and CloudFront’s regional edge caches sit between origins and POPs with larger caches, which AWS explicitly cites for user-generated video and photos that become less popular over time ([Getting Started with MediaConvert Using the API (AWS)](https://docs.aws.amazon.com/mediaconvert/latest/apireference/custom-endpoints.html); [How CloudFront delivers content (AWS)](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.md)). Presigned URL TTLs should be minutes, not the 7-day maximum, because a leaked long-lived URL is a long-lived write capability. Transcoding should scale on queue depth, so an upload spike becomes queue depth while the API stays fast; serving image bytes through app workers is the common cause of “we scaled the web tier and it did nothing”.

Abuse protection must be layered because each layer sees a different identity. At the edge/CDN+WAF, apply coarse per-IP rate limits, bot mitigation and volumetric protection before traffic costs anything: AWS WAF rate-based rules aggregate by IP, use an evaluation window of 60, 120, 300 or 600 seconds (300 default), support a minimum rate of 10, and explicitly do not guarantee an exact limit match ([Using rate-based rule statements in AWS WAF](https://docs.aws.amazon.com/waf/latest/developerguide/waf-rule-statement-type-rate-based.html); [Rate-based rule high-level settings in AWS WAF](https://docs.aws.amazon.com/waf/latest/developerguide/waf-rule-statement-type-rate-based-high-level-settings.html)). WAF Bot Control has Common (self-identifying bots) and Targeted (rate limiting, CAPTCHA, browser challenges, ML) levels, incurs additional fees and is documented at 50 WCUs ([AWS WAF Bot Control rule group](https://docs.aws.amazon.com/waf/latest/developerguide/aws-managed-rule-groups-bot.html)). At the gateway, enforce per-key quotas and request validation; API Gateway’s account-level throttle cannot be exceeded by API/stage/method targets ([Throttle requests to your REST APIs for better throughput in API Gateway](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-request-throttling.html)). Cloud Armor offers throttle and rate-based ban rules applied per backend ([Rate limiting overview (Google Cloud Armor)](https://cloud.google.com/armor/docs/rate-limiting-overview)). Inside the service, enforce per-user token buckets for posts/minute, follows/hour and likes/minute, because carrier-grade NAT puts thousands of users behind one IP and per-IP limits alone are both too loose and too tight. Under a viral spike, shed expensive writes and search/timeline rebuilds with 429/Retry-After while cheap reads come from CDN/cache, so degradation is ordered rather than uniform.

Deployment should be containers on a managed orchestrator, one image per deployable, progressive traffic shifting, feature flags and infrastructure as code. ECS blue/green supports Canary, Linear and All-at-once; predefined configurations include `ECSCanary10Percent5Minutes` and `ECSCanary10Percent15Minutes`, and the deployment group can stop on CloudWatch alarms ([CodeDeploy blue/green deployments for Amazon ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-bluegreen.md)). Canary at 10% for 5–15 minutes with automatic rollback on 5xx rate, p95 latency and queue age is the sweet spot; all-at-once belongs in non-production, and linear is for changes that need a long bake. Feature flags decouple deploy from release—AppConfig supports gradual release, monitoring and instant rollback, including entity-based deployments that keep a user on a configuration version for the deployment period ([What is AWS AppConfig?](https://docs.aws.amazon.com/appconfig/latest/userguide/what-is-appconfig.html)). Schema changes must be backward compatible (expand/contract) because old and new versions run simultaneously during the shift, and infrastructure as code should cover the load balancer, target groups, autoscaling policies, WAF rules, queues and alarms. Shopify’s warning that pipelines are expensive to create, customise and maintain is the argument for keeping the number of deployables small ([Deconstructing the Monolith (Shopify Engineering)](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity)).

## Serve the world from one region behind a CDN until latency or residency forces otherwise

The only well-documented latency budgets are generic web thresholds, not social-feed targets. Good INP is 200 ms or less at the 75th percentile and poor is over 500 ms; INP measures the delay until the next paint and explicitly excludes subsequent network fetches ([web.dev, Interaction to Next Paint](https://web.dev/articles/inp)). TTFB is the sum of redirect, DNS, connection/TLS and server response time, and most sites should target 0.8 seconds or less ([web.dev, Time to First Byte](https://web.dev/articles/ttfb)). No authoritative source publishes p50/p95 budgets for timeline load, post, like or follow, so the split has to be designed: HTML shell and static assets from edge cache, API/timeline reads bounded by one origin round trip, and optimistic UI inside the 200 ms INP budget. CDNs remove the origin leg for cacheable content and repeat visitors: `stale-while-revalidate` lets Cloudflare serve an expired object immediately while revalidating asynchronously, provided the origin sends the directive ([Cloudflare Cache docs, Revalidation](https://developers.cloudflare.com/cache/concepts/revalidation/)), and 0-RTT resumption removes a handshake round trip for returning clients ([Cloudflare docs, 0-RTT Connection Resumption](https://developers.cloudflare.com/speed/optimization/protocol/0-rtt-connection-resumption/)). Physics sets a floor for uncacheable requests: fibre propagates at roughly two-thirds of c, so 10,000 km one-way implies ~100 ms RTT before server time; transpacific or Europe–APAC API calls will sit at 150–250 ms even with a perfect stack.

Two traffic models are in circulation and they matter. A naive 1 request per user per day model makes 1M users/day about 12 rps; a social-feed model at 40 requests per user per day makes it ~463 rps average and ~1,400 rps at a 3× peak. The second is the safer planning basis because Twitter’s documented read/write shape was ~50:1, but both are assumptions until replaced by telemetry. At either level, a single region plus CDN is defensible; the 12 rps model makes multi-region obviously unnecessary, while the read-heavy model still fits one region with regional cache and read replicas.

Static assets, media and a cacheable app shell belong on the CDN; per-user API responses and WebSocket fan-out belong at edge compute or stateful edge objects, not in a shared cache. CloudFront signed URLs embed an expiration and signature and support RSA 2048 and ECDSA 256 keys for time-limited access to individual objects ([AWS CloudFront docs, Use signed URLs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html)). Cloudflare Durable Objects can act as WebSocket servers, connect thousands of clients per instance, and use a Hibernation API that evicts the object from memory while clients stay connected, with no billable duration while hibernating ([Cloudflare Durable Objects docs, Use WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)). Edge compute has hard limits: Workers Free provides 10 ms CPU and 50 subrequests, Workers Paid 5 minutes CPU (default 30 s) and 10,000 subrequests per request ([Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). That is enough to authenticate and fan out, not to run feed ranking. Google Cloud CDN serves cache hits directly from the GFE nearest the user and falls back to origin only on a miss ([Google Cloud CDN overview](https://cloud.google.com/cdn/docs/overview)); Fastly’s Compute uses shield POPs to designate which POP talks to the origin ([Fastly docs, Using Fastly's global POP network](https://www.fastly.com/documentation/guides/getting-started/concepts/using-fastlys-global-pop-network)).

The region path should be staged. Step one is one region plus CDN, which keeps a single writer and no consistency problem. Step two adds read replicas or caches per region: Aurora Global Database uses storage-based replication with typical latency under 1 second, an effective RPO of 1 second and an RTO under 1 minute, and can promote a secondary to read/write in under a minute ([AWS, Amazon Aurora Global Database](https://aws.amazon.com/rds/aurora/global-database/)); binlog-based cross-region replication, by contrast, can lag indefinitely as write rate rises ([AWS Aurora FAQs](https://aws.amazon.com/rds/aurora/faqs/)). Step three is active-active writes, where DynamoDB global tables default to whole-item last-writer-wins reconciliation, so concurrent updates to different attributes of the same item in different regions can be lost ([AWS docs, Global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GlobalTables.html)). CRDT-style application merge is the secondary recommendation for counters and lists ([FactualMinds, CRDTs vs Last-Write-Wins on AWS](https://www.factualminds.com/blog/crdts-vs-last-write-wins-on-aws/)). Aurora Global Database also pauses writes if RPO lag in all secondary regions exceeds the configured limit, making replication health a write-availability dependency ([AWS, Boost Performance of Global Applications with Aurora Global Database](https://pages.awscloud.com/rs/112-TZM-766/images/Aurora_Global_Database.pdf)). Read-your-writes needs either an author-session primary read or a per-user version token; otherwise a user who posts and refreshes from a lagging replica sees a missing post.

DNS and anycast solve different problems. Route 53 latency-based routing answers with the region measured to give the user the lowest latency ([AWS docs, Latency-based routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-latency.html)), while Global Accelerator uses anycast IPs to route to the nearest healthy endpoint over the AWS backbone ([AWS, Use AWS Global Accelerator to improve application performance](https://aws.amazon.com/global-accelerator/)). DNS decisions happen during resolution and are subject to resolver caching, so failover can be slower; anycast reroutes on continuous health checks without waiting for TTL expiry, but a long-lived WebSocket may be re-routed mid-session and must reconnect idempotently ([AWS Builder Center, Global Accelerator vs Route 53 for multi-Region failover](https://builder.aws.com/)). Use latency routing for speed, geolocation for residency, failover for active-passive DR and weighted records for canary ([AWS system-design reference notes (agent_setup)](https://github.com/phamvantienkiz/agent_setup)). Residency cannot be guaranteed by geo-DNS alone; enforce it in the application/auth layer.

Legal residency constrains where data can live, but less uniformly than “GDPR means EU data stays in the EU”. GDPR permits transfers only with an adequacy decision (Art. 45), or appropriate safeguards such as SCCs plus enforceable rights (Art. 46), or a specific derogation (Art. 49) ([CJEU press release No 91/20, Case C-311/18 (Schrems II)](https://curia.europa.eu/jcms/upload/docs/application/pdf/2020-07/cp200091en.pdf)). Schrems II invalidated the EU–US Privacy Shield while upholding SCCs, and exporters relying on SCCs must assess destination law and adopt supplementary measures under the EDPB’s six-step approach ([EDPB, Recommendations 01/2020](https://www.edpb.europa.eu/our-work-tools/our-documents/recommendations/recommendations-012020-measures-supplement-transfer_en)). The EU–US Data Privacy Framework was upheld by the EU General Court on 3 September 2025 in Case T-553/23, but appeals are expected/underway, so an SCC plus transfer-impact-assessment fallback should remain in place ([Freshfields](https://www.freshfields.com); [MLex](https://www.mlex.com)). The DSA’s platform-specific obligations attach at more than 45 million average monthly EU users, with four months to comply after designation, including systemic-risk mitigation, an independent annual audit, data sharing, a non-profiled recommender option and a public ad repository ([European Commission, DSA: Very large online platforms and search engines](https://digital-strategy.ec.europa.eu/en/policies/dsa-vlops)). California’s CCPA/CPRA grants rights to know, delete, opt out of sale/sharing, correct and limit sensitive data use ([California OAG, CCPA](https://oag.ca.gov/privacy/ccpa)). India’s DPDP Act permits transfer except to blacklisted countries and has no general localisation mandate, but RBI has required payment-system data to be stored only in India since 15 October 2018, and Significant Data Fiduciaries may be required to keep government-specified data in India ([DLA Piper, Data Protection in India – Transfer](https://www.dlapiperdataprotection.com/?t=transfer&c=IN)). Russia is the hard case: Federal Law 242-FZ requires databases with Russian citizens’ personal data to be in Russia, and amendments from 1 July 2025 tighten this so operators must use Russian databases when collecting personal data, with further restrictions on foreign databases ([Denuo](https://denuo.legal/en/insights/tougher-personal-data-localisation-requirements-from-1-july-2025/); [Digital Watch Observatory](https://dig.watch)). Brazil’s LGPD regulates transfers through adequacy and contractual clauses under ANPD Resolution 19/2024, with a 12-month adaptation period and no prior authorisation ([Baker McKenzie](https://resourcehub.bakermckenzie.com); [Chambers](https://gpg-pdf.chambers.com)). A single EU or US region can legally serve EU users with a transfer mechanism; Russia effectively requires a separate in-country database or a decision not to serve Russia.

Multi-region cost is real but poorly benchmarked. Inter-region data transfer out of us-east-1 is commonly quoted at ~$0.02/GB, and cross-AZ transfer at $0.01/GB each direction ([Eon](https://www.eon.io); [FactualMinds](https://www.factualminds.com)). Third-party analyses estimate active-active multi-region at 2–3× compute versus single-region multi-AZ, plus 10–20% of the bill in cross-region transfer, plus conflict-resolution work ([engineering-handbook](https://github.com/handbook-academy/engineering-handbook)). Global Accelerator is billed per accelerator-hour (~$0.025/hour, charged even when disabled) plus a data-transfer premium ([FactualMinds](https://www.factualminds.com)), and Aurora Global Database requires a full copy of the database in each secondary region, so setup time and storage scale with database size ([AWS docs, Comparing Amazon Aurora replication solutions](https://docs.aws.eu)). No source explicitly states “single region + CDN is sufficient at 1M DAU”; that conclusion is an inference from the traffic arithmetic and the absence of any published multi-region cost benchmark at this scale. The economical intermediate step is one read replica in the largest far-away region, not active-active everywhere.

Realtime delivery should assume mobile networks will break sockets. Two workable patterns exist: terminate WebSockets at an edge platform with hibernation/stateful objects, or use a managed global pub/sub with an edge entry point. Ably publishes ~37 ms global median RTT, <65 ms global p99, 6.5 ms in-region delivery and <30 ms datacenter p99 ([Ably, Four Pillars of Dependability](https://ably.com/four-pillars-of-dependability)). Mobile carrier NAT idle timeouts are commonly 30–60 s, so an unconfigured heartbeat leads to silent connection death; long polling carries full HTTP headers per message and is much less efficient ([Volcengine](https://www.volcengine.com)). IETF guidance notes UDP timeouts around 30 s and TCP timeouts from 1 to 60 minutes, requiring keepalives and client re-initiation ([IETF](https://www.ietf.org)). Android Doze suspends network access during idle and batches it into maintenance windows, breaking WebSockets ([Microsoft Q&A](https://learn.microsoft.com)). Model live updates as best-effort deltas over a socket plus a catch-up fetch on reconnect; correctness should come from a durable queue/outbox and client sequence numbers, with APNs/FCM carrying anything that must arrive while the app is backgrounded. Connection-count and fan-out limits for Durable Objects, and per-connection pricing at 1M users, were not established from primary sources.

## Reliability, security, cost and migration form one gate, not four workstreams

A 99.9% availability SLO over a 28-day window for feed read, post create and login is the honest ceiling for a small team; 99.99% implies multi-region automatic failover, no single points of failure and a staffed team. Google’s example error-budget policy halts all changes and releases other than P0/security fixes when the four-week budget is exhausted, requires a postmortem with a P0 action item when a single incident consumes more than 20% of the budget, and escalates disputes to the CTO ([Google SRE Workbook, Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/)). A 99.9% SLO gives a budget of 1,000 errors per 1M requests, and Google notes changes cause roughly 70% of outages. 99.9% over 30 days is 43.2 minutes of allowed unavailability; multi-window burn-rate alerts—fast (1h/5m, 2% budget), slow (6h/30m, 5%) and ticket (3d/6h, 10%)—are the recommended pattern ([SLO principles](https://github.com/alirezarezvani/claude-skills/blob/9ca476d8401f8750f92f4a7b31ec68efaa61ab02/engineering/skills/slo-architect/references/slo_principles.md); [Google SRE Workbook, Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)). No official social-platform SLO document was found; Twitter’s open-sourced For You config reports p99 warning at 2,800 ms and critical at 3,000 ms with success-rate warning below 99.9%, but that is a secondary compilation for a ranking pipeline, not basic timeline reads ([raw.githubusercontent.com compilation](https://raw.githubusercontent.com)). A defensible small-team target is p95 <300 ms and p99 <800 ms server-side for feed read, p95 <500 ms for post create, plus a freshness SLI of new posts visible to followers within 30 s—these are estimates to calibrate, not published standards.

Observability should be OpenTelemetry-shaped instrumentation shipped to one managed backend, with cardinality and log volume treated as cost controls. Grafana Cloud’s free tier includes 10k active series and 50 GB each of logs, traces and profiles with 14-day retention; Pro starts at $19/month platform fee plus $6.50/1k series and log pricing of $0.050/GB process, $0.400/GB write and $0.100/GB retain, with 13-month metrics retention ([Grafana Labs pricing](https://grafana.com/pricing/)). Sentry Developer is free at 5k errors/month and 1 user; Team is $26/month annual ($29 monthly) with unlimited users, 50k errors, 5M spans and 30-day lookback ([Sentry pricing](https://sentry.io/pricing/)). PostHog’s first 1M events/month are free ([PostHog pricing](https://posthog.com/pricing)). Datadog bills host products on a high-water-mark of the lower 99% of hourly host counts and custom metrics by cardinality ([Datadog docs, Pricing](https://docs.datadoghq.com/account_management/billing/pricing/)); third-party summaries list Infrastructure at $15–23/host/month, APM at $31–40/host/month, log ingestion at $0.10/GB, indexing at $1.70 per million events at 15 days ($2.50 at 30 days), and RUM at $1.50 per 1,000 sessions, so 2M sessions/month alone is $3,000 ([DoiT](https://www.doit.com); [OneUptime](https://oneuptime.com); [SaaSCompared](https://saascompared.com)). Datadog’s own list price page was not opened, so these are third-party figures. The two dangerous dimensions are log volume and metric cardinality; user ID or request ID as a metric label multiplies series unboundedly, and observability shipping is reported as 30% of egress in many setups ([Sedai](https://sedai.io); [zop.dev](https://zop.dev)).

Load and failure testing should use the k6 ladder: smoke, average-load, stress, soak, spike and breakpoint, with load and stress typically 5–60 minutes, soak hours, and spike a few minutes ([Grafana k6 docs, Load test types](https://grafana.com/docs/k6/latest/testing-guides/test-types/)). Gate releases on an average-load run that holds the SLO, run a 3–6 hour soak before major releases to catch leaks and pool exhaustion, and run a quarterly game day using fault injection with stop conditions. AWS Well-Architected FND04-BP08 calls for bounded experiments with stop conditions, scope-of-impact controls and approval gates, and names “running chaos experiments in production without stop conditions” and “game days only in non-production” as anti-patterns; AWS FIS supports EC2, ECS, EKS, RDS and network-path experiments including AZ impairment, region-scale impact, instance interruption and packet loss ([AWS Well-Architected FND04-BP08](https://docs.aws.amazon.com/wellarchitected/latest/framework/fnd04-bp08.md)). Chaos experiments should define steady state as measurable throughput, error rates and latency percentiles, and try to disprove the hypothesis ([Principles of Chaos Engineering](https://principlesofchaos.org/)). Provision for peak, not average: daily peak-to-mean ratios of 3–5× are typical, and with three AZs each must absorb 50% more load to lose one failure domain ([ultimate-devops-guide](https://github.com/mchittineni/ultimate-devops-guide/blob/81984086528885cf0aada703eb45c7c454ed40b5/site-reliability-engineering/how-do-you-do-capacity-planning.md)). Size from a load-tested per-unit limit at 60–70% target peak utilisation and pre-provision anything whose scaling lead time exceeds the spike rise time ([LunaStack](https://github.com/moonshineaitech/LunaStack/blob/main/wiki/skills/ops/capacity-planning.md)). At the 40-requests/user/day model, a release gate of ~1,500–2,000 rps sustained is the right test range; at 1M requests/day, it is trivial.

Backups and disaster recovery should be designed for “cannot afford data loss” without overbuying. RDS automated backups provide point-in-time recovery with retention from 1 to 35 days, and restores can go back to any point within the retention period with 1-second precision; the latest restorable time is typically within the last 5 minutes ([AWS docs, Introduction to backups (RDS)](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html)). AWS’s DR ladder maps Backup & Restore to RPO/RTO in hours, Pilot Light to tens of minutes, Warm Standby to minutes, and Multi-site active-active to real time, and continuous replication alone “copies corruption and deletion to the recovery site as faithfully as it copies good data”, so PITR is mandatory at every tier ([AWS whitepaper, Disaster recovery options in the cloud](https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html)). At launch, set RPO ≤5 minutes and RTO ≤4 hours for the primary database: PITR on, daily snapshots copied cross-region, replication-lag monitoring, and a tested restore runbook. Aurora MySQL Backtrack can rewind a cluster in seconds without restoring from backup, but the window is capped at 72 hours and it is not a substitute for cross-region backups ([AWS docs, Amazon Aurora Backtrack](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Monitoring.Metrics.html)). AWS Backup pricing is roughly $0.05/GB-month warm, $0.01/GB-month cold with a 90-day minimum, and $0.02/GB cross-region copy for S3/EBS/RDS/Aurora ([FactualMinds, AWS Backup pricing](https://www.factualminds.com); [Eon, AWS Backup pricing](https://www.eon.io)). GDPR Art. 32 explicitly requires timely restoration and “a process for regularly testing” it, so restore drills are a compliance control, not just an ops nicety ([GDPR Art. 32](https://gdpr-info.eu/art-32-gdpr/)). Failback to the primary site needs its own documented plan; recovery is not complete when the secondary takes over ([AWS Well-Architected REL13-BP02](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel13-bp02.md)).

Security at launch means correct credential storage, MFA, OIDC, secrets management, encryption, least privilege, DDoS protection and abuse reporting. OWASP recommends Argon2id with a minimum of 19 MiB memory, 2 iterations and 1 degree of parallelism; the higher-security profile is 46 MiB and 1 iteration; scrypt, bcrypt (work factor ≥10, 72-byte limit) and PBKDF2 (≥600,000 iterations with HMAC-SHA-256) are fallbacks, and fast hashes such as SHA-256 are unsuitable ([OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). Store the algorithm and parameters per row so hashes can be re-derived on next login. ASVS 5.0 requires 8 characters at L1 and 12 at L2, breached-password checks, authentication rate limiting, session tokens of at least 128 bits of entropy, MFA for sensitive operations at L2 and a phishing-resistant factor at L3; V6.1.3 requires every authentication pathway—password, social/OIDC, magic link, recovery—to be documented and enforced consistently ([ASVS v5.0.0 chapters V6–V10 (mirror)](https://cdn.jsdelivr.net); [ASVS 5.0 V6.1.3](https://safeguard.sh)). OIDC social login reduces password surface but adds account-linking risk, so the “document every pathway” control matters. AWS Secrets Manager costs about $0.40 per secret per month plus $0.05 per 10,000 API calls, with no permanent free tier; SSM Parameter Store standard is free ([AWS Builder Center](https://builder.aws.com); [Akeyless](https://www.akeyless.io); [Steve Kinney](https://stevekinney.com)). Shield Standard is free for L3/4; Shield Advanced is $3,000/month per organisation with L3/4/7 protection, bundled WAF and DDoS cost protection on a one-year commitment ([AWS Shield pricing](https://aws.amazon.com/shield/pricing/)). For a startup, Shield Standard plus CloudFront/WAF rate rules and provider-level DDoS absorption is proportionate; Shield Advanced becomes justified after a real volumetric/extortion attack or when its cost-protection guarantee exceeds the subscription. GDPR Art. 32 requires pseudonymisation/encryption, confidentiality/integrity/availability/resilience and instruction-bound processing ([GDPR Art. 32](https://gdpr-info.eu/art-32-gdpr/)); the DSA imposes notice-and-action, statements of reasons and criminal-offence notification on hosting services, but micro and small enterprises are exempt from the platform-specific section except Art. 24(3) ([Cooley, EU DSA](https://www.cooley.com); [Springlex, DSA Art. 19](https://www.springlex.eu)). Dependency and supply-chain scanning (SBOM, SLSA, Dependabot/Snyk) was not covered by a primary source here and should be treated as an open mandatory item, as should specific KMS key-rotation and TLS-minimum settings beyond GDPR’s general requirement.

The dangerous multipliers are egress, observability ingest and managed-database I/O/storage. Doubling media per post roughly doubles the ~$6.5k CDN line to ~$13k; adding RUM at 2M sessions/month adds ~$3,000 on Datadog; Multi-AZ doubles database cost and backup storage beyond the free allowance adds another line. CloudFront in front of S3, a Savings Bundle, trace sampling, debug-log dropping and bounded metric labels are the cost levers. No published total monthly cost for a 1M-DAU social app was found, and managed-DB IOPS pricing was not researched, so the table is a budgeting model, not a quote.

Team and process need four artefacts more than tools: a primary/secondary on-call rotation with a stated paging response time, a blameless postmortem process with pre-agreed triggers, tested runbooks for restore/failover/cache loss/rollback, and a quarterly capacity review tied to the error-budget policy. Google’s norms put the minimum single-site on-call team at eight engineers with week-long shifts, or six per site for a dual-site team, cap purely operational work at 50% of an SRE’s time, and set paging response at 5 minutes for user-facing services and 30 minutes for less time-sensitive systems ([Google SRE Book, Being On-Call](https://raw.githubusercontent.com/euclid1990/google-sre-book/master/Site%20Reliability%20Engineering.pdf)). Below eight engineers, a reliable 24/7 rotation is not staffable; the correct substitute is managed services with vendor SLAs and an explicit acceptance of the vendor’s RPO/RTO, not a promise the team cannot keep. Postmortem triggers should be defined before an incident: user-visible downtime or degradation beyond a threshold, any data loss, on-call intervention, resolution time above a threshold, and monitoring failure; the process must identify contributing causes without indicting individuals ([Google SRE Book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)). Game days should exercise the teams and runbooks, not just infrastructure ([AWS Well-Architected FND04-BP08](https://docs.aws.amazon.com/wellarchitected/latest/framework/fnd04-bp08.md)), and the quarterly capacity review should record the load-tested per-unit limit, current peak, headroom factor and the date projected growth breaches 70% utilisation ([LunaStack](https://github.com/moonshineaitech/LunaStack/blob/main/wiki/skills/ops/capacity-planning.md)).

Migration failure modes are overwhelmingly about unverified assumptions and unrehearsed rollback, not the tools. RevenueCat’s cutover is the cautionary case: a planned <10-second write freeze became a ~3.5-hour degradation because `ANALYZE` had not run on the largest table, primary-key sequences were not replicated, and dry runs tested reads but not writes; rollback required reversing replication and shifting traffic back with writes blocked, and the team concluded an earlier rollback would have been better ([RevenueCat postmortem](https://www.revenuecat.com/blog/engineering/postmortem-aurora-postgres-migration)). The cutover also ran before Thanksgiving with part of the support team on holiday, and an APM agent issuing `EXPLAIN` on slow queries amplified the incident. Database-level replication is safer than application-level dual writes, which risk silent divergence and need reconciliation plus a “Do-Not-Load” table to avoid re-inserting rows deleted before backfill ([AWS Builder Center: The Dual Write Pattern, part 2 — Pitfalls](https://builder.aws.com/content/3HHcHPT33Ja94wdrl4fPLiBXTaQ/the-dual-write-pattern-part-2-pitfalls)). Vitess MoveTables formalises the safe sequence: create workflow, monitor, confirm with VDiff, `switchtraffic`, complete; `switchtraffic` supports dry-run, refuses to switch while replication lag exceeds the default 30 s threshold, and sets up reverse replication by default ([Vitess MoveTables](https://vitess.io/docs/25.0/reference/vreplication/movetables/); [vtctldclient MoveTables switchtraffic](https://vitess.io/docs/archive/20.0/reference/programs/vtctldclient/vtctldclient_movetables/vtctldclient_movetables_switchtraffic/)). Etsy rehearsed against a full clone of production with all replicas and the full 40-shard destination, and still hit a 40× query-volume jump (≈5k/s to ≈200k/s) when a non-sharding-column query became scatter-gather across all shards; it switched back, built secondary vindexes in staging and rolled forward, and later found that switching writes back stopped lookup-table population and broke the derived vindexes ([Etsy Engineering](https://www.etsy.com/il-en/codeascraft/scaling-etsy-payments-with-vitess-part-2--the-seamless-migration)).

Schema changes need expand → migrate → contract. Parallel Change supports both old and new forms, moves consumers, then removes the old form, and allows release in any phase ([martinfowler.com: Parallel Change](https://martinfowler.com/bliki/ParallelChange.html)). gh-ost creates a ghost table, copies data incrementally, reads ongoing changes from the binary log rather than triggers, and performs an atomic two-step rename that either succeeds or returns to the pre-cutover state with the original table intact; it can postpone cutover with a flag file and test the whole flow on a replica ([gh-ost README](https://raw.githubusercontent.com/soepic1/gh-ost/refs/heads/master/README.md); [gh-ost cut-over](https://github.com/pengan1990/gh-ost/blob/master/doc/cut-over.md)). pt-online-schema-change uses triggers instead, will not work if triggers already exist, but supports resuming after interruption (`--resume` with `--history`, `--nodrop-new-table`, `--nodrop-triggers`), whereas gh-ost has no equivalent resume and a dead process loses the migration ([pt-online-schema-change manpage](https://manpages.ubuntu.com/manpages/jammy/man1/pt-online-schema-change.1.html); [Bytebase](https://www.bytebase.com/blog/gh-ost-vs-pt-online-schema-change/)). Derived structures—caches, search indexes, lookup tables, materialised feeds—must be in the rollback plan; Etsy’s vindex incident shows a data rollback can leave derived state permanently wrong. Feature-flag rollouts should go 1% → 5% → 25% → 100%, with shadow traffic first; LaunchDarkly’s percentage rollouts hash the context key into 100,000 buckets for deterministic stickiness and support values below 1% ([LaunchDarkly: Percentage rollouts](https://launchdarkly.com/docs/home/releases/percentage-rollouts)). Cache invalidation needs single-flight or probabilistic early expiry before the cache becomes load-bearing; a stampede turns a cache problem into a database outage, as Wikimedia’s incident record describes when stampede protection regressed ([Wikimedia Phabricator T443065](https://phabricator.wikimedia.org/T443065)). RevenueCat tuned caches to short TTLs before cutover and stopped non-web jobs during the switch, a pattern worth copying.

## Conclusion

The durable architectural answer is to keep the relational database as the source of truth for users, credentials and posts, but stop asking it to serve every read and every counter write. Precomputed home timelines, cache-aside in Redis, sharded or asynchronous counters, object storage plus CDN for media, and queue-driven fan-out/notifications remove the work that would otherwise force sharding at 1M DAU. The application tier should remain a modular monolith with two or three extracted workers/services, a stateless request path, presigned uploads, idempotent writes and a single canary/rollback pipeline. Operationally, 99.9% is the right first SLO, the observability bill and CDN egress are the costs that scale faster than users, and the migration must be gated on rehearsed rollback, `ANALYZE`/sequence checks, shadow traffic and a reverse-replication soak.

The honest uncertainties are as important as the recommendations. The per-DAU traffic ratios, 0.5–1 KB post sizes, 40 requests/user/day, $11k–13k total cost and 1,500–2,000 rps release gate are planning estimates, not sourced benchmarks; MySQL’s ~5k writes/s ceiling is practitioner guidance, not a vendor specification; no source gives a precise DAU threshold for sharding or a published latency budget for social-feed interactions; and the legal residency position is unsettled—the EU–US Data Privacy Framework survived its first challenge but remains appealable, while Russia’s 2025 amendments are the one clear case where a separate in-country database is unavoidable. If the real load is 1M requests/day, most of this report reduces to a managed MySQL instance, one cache and a CDN. If it is 10M DAU, the write ceiling is crossed, sharding or a distributed SQL/wide-column store becomes mandatory, and the cost moves from thousands to tens of thousands per month.
