# Scaling a Twitter-like App to a Million Daily Users

One million daily users translates to roughly **12 events per second** for every one action per user per day ([sujeet.pro capacity notes](https://github.com/sujeet-pro/sujeet.pro/blob/main/content/articles/capacity-planning-and-estimation)), and at the only first-hand read/write ratio published by a Twitter-like service — **300,000 timeline-read QPS against 6,000 tweet-write QPS, about 50:1** ([High Scalability, 2013](http://highscalability.squarespace.com/blog/2013/7/15/ask-hs-whats-wrong-with-twitter-why-isnt-one-machine-enough.html)) — that scales to about **2,000 timeline reads/s and 40 post writes/s on average**, or roughly 10,000 reads/s and 200 writes/s at a 5× peak. A single MySQL primary can absorb that write volume; what it cannot absorb is the read amplification and connection churn that a social feed creates, which is why the first wall is connection exhaustion and per-request fan-out queries rather than the 64 TB table limit ([MySQL 8.0 Reference Manual, 10.4.6](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/table-size-limit.html)). The evidence points to an ordered programme rather than a rewrite: put a connection pooler and a timeline cache in front of the existing database, add a read replica, move media to object storage behind a CDN, move fan-out and notification work onto a queue via a transactional outbox, split the schema by domain, and only then shard by user and add a read region elsewhere. Every step on that list is documented in a first-party engineering account as a prerequisite for the next, and the teams that skipped to sharding spent years retrofitting ([GitHub](https://github.blog/engineering/partitioning-githubs-relational-databases-scale/); [Shopify](https://shopify.engineering/horizontally-scaling-the-rails-backend-of-shop-app-with-vitess)). The unresolved question is not architecture but budget: published estimates for a managed stack at this size span **$10,000 to $100,000 per month** ([SpendArk](https://spendark.com/blog/cloud-cost-per-user/)), with media egress and logging as the swing factors.

## One million daily users means about 2,000 timeline reads a second, and connections break first

Two definitions matter before any number. **Daily active users (DAU)** is the count of distinct accounts performing at least one action per day; the largest published Twitter-like figures use "active users" (150M worldwide) without distinguishing daily from monthly, so any 1M-DAU projection is an interpolation rather than a measured load ([High Scalability, 2013](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/)). **Peak-to-average ratio** is the multiplier between mean and busiest-hour traffic; published assumptions run from 2× to 10×, with 5–10× stated for social media and 5× used in a worked Twitter-at-scale example ([skillui.com](https://www.skillui.com); [semicolony.dev](https://semicolony.dev)). Because that spread is a factor of five, the only defensible input is the client's own measured diurnal curve.

| Derived load at ~1M DAU | Average | At 5× peak | Basis |
|---|---|---|---|
| Timeline reads | ~2,000 /s | ~10,000 /s | 300K read QPS at 150M users ([High Scalability](http://highscalability.squarespace.com/blog/2013/7/15/ask-hs-whats-wrong-with-twitter-why-isnt-one-machine-enough.html)) |
| Post writes | ~40 /s | ~200 /s | 6K write QPS at 150M users (same) |
| Text storage | ≲1–3 GB/day | — | 300–500 B per post, 3× replication ([High Scalability](http://highscalability.squarespace.com/blog/2013/7/15/ask-hs-whats-wrong-with-twitter-why-isnt-one-machine-enough.html); [skillui.com](https://www.skillui.com)) |
| Follow graph | ~10–30 GB | — | ~200 follows/user × 1M, 40–80 B/row |

These are arithmetic scalings, not published 1M-DAU plans; **no vendor, peer-reviewed study or platform engineering blog publishes a capacity plan for a 1M-DAU Twitter-like app**, and no source quantifies follow/unfollow or notification write rates at that size.

The realistic first failure is the connection path. MySQL's `max_connections` defaults to **151**, and the manual notes the server actually admits `max_connections + 1` clients ([MySQL 8.0 Reference Manual, B.3.2.5](https://dev.mysql.com/doc/refman/8.0/en/too-many-connections.html)). Per-connection buffers typically consume **2–4 MB, up to 10–20 MB with custom sizing**, so 151 connections is a memory decision as well as a concurrency one, and the practical guidance is to stay at **1,000–2,000 connections behind a pooler such as ProxySQL** before raising the limit further ([OneUptime](https://github.com/OneUptime/blog)). The second failure is the read pattern: early Twitter inserted each tweet into a replicated MySQL database and then, at read time, looked up the follower list in memcached and **issued one SELECT per followed account**, a design that left the service down "about half the time" ([High Scalability](http://highscalability.squarespace.com/blog/2013/7/15/ask-hs-whats-wrong-with-twitter-why-isnt-one-machine-enough.html)); Twitter's own 2008 account describes one write database with multiple read slaves, hand-tuned replication and memcached "to minimize our reliance on a database" ([Twitter Blog, 2008](https://blog.x.com/en_us/a/2008/its-not-rocket-science-but-its-our-work)).

Raw write capacity is not the constraint. Published single-server figures span roughly **2,000–30,000 inserts/s**, with the order of magnitude set by durability settings (`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`) rather than hardware ([lvdaxianerplus](https://www.lvdaxianerplus.cc)), and vendor benchmarks report 15,714 QPS / 785 TPS on a 2-core NVMe instance ([UCloud](https://docs.ucloud.cn)) and 80,645 QPS on a 28-core machine ([Baidu Cloud](https://cloud.baidu.com)); those workloads are not comparable and **no official MySQL documentation states a maximum write QPS**. Table size is likewise a multi-year problem for text — InnoDB caps a table at **64 TB** and recommends partitioning above **1 TB** — but becomes immediate if images are stored as BLOBs ([MySQL 8.0 Reference Manual, 10.4.6](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/table-size-limit.html); [InnoDB Limits](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-limits.html)).

## Keep MySQL, cache timelines, and shard only after schemas are separated

The strongest first-party evidence for social workloads points to sharded relational storage, not wholesale replacement. Slack serves **2.3 million QPS at peak — 2M reads and 300K writes — at a median of 2 ms and p99 of 11 ms** through Vitess on sharded MySQL, sharded by workspace ID ([Slack Engineering](https://slack.engineering/scaling-datastores-at-slack-with-vitess/)). Slack explicitly **ruled out DynamoDB, Cassandra, Spanner and CockroachDB** on grounds of thousands of MySQL-specific queries and years of operational practice. Shopify moved from a single MySQL primary — where schema migrations "would take weeks" — to federation, then Vitess with `user_id` as sharding key and tables holding **billions of rows** ([Shopify Engineering](https://shopify.engineering/horizontally-scaling-the-rails-backend-of-shop-app-with-vitess)). Pinterest sharded MySQL in 2012 and still calls it the system that stores core data, with **more than 50 billion Pins on one billion boards**, after several NoSQL technologies "broke catastrophically" ([Pinterest Engineering](https://medium.com/@Pinterest_Engineering/sharding-pinterest-how-we-scaled-our-mysql-fleet-3f341e96ca6f)).

| System | Store | Published scale | Transferable lesson |
|---|---|---|---|
| Slack | Sharded MySQL + Vitess | 2.3M QPS peak ([Slack](https://slack.engineering/scaling-datastores-at-slack-with-vitess/)) | Shard key = tenant; proxy before shards |
| Shopify | MySQL + Vitess, `user_id` key | Billions of rows per table ([Shopify](https://shopify.engineering/horizontally-scaling-the-rails-backend-of-shop-app-with-vitess)) | Federation first, then keyspace split, then shard |
| Pinterest | Bespoke sharded MySQL | 50B pins, 1B boards ([Pinterest](https://medium.com/@Pinterest_Engineering/sharding-pinterest-how-we-scaled-our-mysql-fleet-3f341e96ca6f)) | IDs embed the shard; no cross-shard joins |
| Discord | Cassandra → ScyllaDB | 177 Cassandra nodes → 72 ScyllaDB, trillions of messages ([Discord](https://discord.com/blog/how-discord-stores-trillions-of-messages)) | Wide-column suits append-only, time-partitioned data |

Discord is the documented exception and shows why the wide-column path is workload-specific: it left Cassandra for ScyllaDB because Cassandra was "a high-toil system" with unpredictable latency, on-call paging and hot partitions, and notes that **reads are more expensive than writes** in that model ([Discord](https://discord.com/blog/how-discord-stores-trillions-of-messages)). None of the published scales above is reached at 1M DAU, and **no first-party case study documents a Twitter-like feed on CockroachDB or Spanner** — the absence is a documentation gap, not proof of unsuitability.

Timeline generation is the design decision that determines everything else. Twitter's published design is **fan-out on write**: tweets are pushed into a Redis cluster holding per-user home timelines capped at **800 entries** and appended with `RPUSHX` so only already-cached timelines are written ([High Scalability](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/); [SlideShare, Krikorian](https://www.slideshare.net/slideshow/twitter-raffi-krikoriantimelinesatscale/24038049)). That converts read-time merging into cheap write-time appends — the right trade at a 50:1 read ratio. It breaks on celebrities: fan-out to a 31M-follower account meant a tweet "can take up to 5 minutes" to reach followers against a 5-second target, so Twitter shifted to **doing more work on reads for high-value users**, a hybrid of push and pull ([SlideShare](https://www.slideshare.net/slideshow/twitter-raffi-krikoriantimelinesatscale/24038049); [High Scalability](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/)). Replicate that hybrid from the start with a follower threshold you can tune, and skip dormant accounts. What the sources do not give is the threshold value, per-follower write amplification, or latency distributions, and **no opened source documents how follower counts themselves are cached** — plan them as counters with periodic reconciliation.

Caching in these systems is a materialised ID list, not a generic read-through cache; post bodies are hydrated separately, which is why Twitter says "the text of the tweet is almost irrelevant to most of Twitter's infrastructure" ([High Scalability](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/)). Discord takes a different route worth copying at moderate scale: Rust data services in front of ScyllaDB perform **request coalescing** — concurrent reads of the same row trigger one database query — and consistent-hash routing by channel ID, which "significantly reduce traffic spikes against the database" ([Discord](https://discord.com/blog/how-discord-stores-trillions-of-messages)). The only numeric hit rates encountered (96.4% cache hits, 99.8% reads, for Facebook's TAO) come from secondary summaries of a paper that was not opened, so they should be treated as indicative targets, not measured baselines.

Migration mechanics are well documented and uniformly slow. Shopify's sequence was **Vitessify → dual connectivity → keyspace split → horizontal shard**, and it warns that Vitess's default atomicity allows partial commits: if a cross-shard transaction commits on one shard and fails on another, "the change on SHARD_1 will not be rolled back" ([Shopify Engineering](https://shopify.engineering/horizontally-scaling-the-rails-backend-of-shop-app-with-vitess)). Shopify credits application-level **query verifiers** — catching missing shard keys, cross-shard joins and scatter queries — as the single most important factor, and notes that backfilling a `user_id` column on billions of rows at peak load took far longer than expected. Slack's move took **2017 to end-2020** and required a generic backfill system with double-writes and a parallel double-read diffing system to prove equivalence ([Slack Engineering](https://slack.engineering/scaling-datastores-at-slack-with-vitess/)). Discord migrated trillions of messages in **nine days at up to 3.2 million messages/s**, then stalled at "99.9999% complete" on uncompacted Cassandra tombstones ([Discord](https://discord.com/blog/how-discord-stores-trillions-of-messages)).

## Serve media from object storage and the edge, or pay 75–200 ms per request

The request path itself is uncontentious: a layer-7 load balancer terminating TLS across stateless application servers in multiple availability zones, with **sessions in Redis or signed tokens rather than process memory**, then a cache tier and read replicas in front of the primary ([AWS Well-Architected PERF04-BP06](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf04-bp06.md); [GitHub scaling notes](https://github.com)). Quoted latency must state which path it measures: Twitter's 2013 timeline service ran at **5 ms p50**, while the ranked "For You" timeline runs at **3,000 ms p99** ([Guo-astro engineering handbook](https://github.com/Guo-astro/engineering-handbook/blob/11356c7ef0d4cee1d187e026452c4bbf509bbf38/content/hld/part-8-case-studies/06-social-media-feed.md)). Ship the precomputed chronological timeline first; treat ranking as a separate, slower service.

Media is a different system, not a column. The documented pattern is direct client upload to object storage via pre-signed URLs — "the upload API never touches photo bytes" — a queue-driven worker pool producing a fixed derivative ladder, and a CDN with an **origin shield** collapsing viral stampedes into a single origin fetch ([The HLD Handbook, Photo Sharing](https://hld.handbook.academy/curriculum/case-studies/photo-sharing/)). Design for object-storage request limits: **3,500 PUT/s and 5,500 GET/s per prefix**, a 48.8 TiB maximum object, multipart uploads of 5 MiB–5 GiB up to 10,000 parts (same source). Twitter's operational lesson is to decouple upload from posting, use segmented resumable uploads, and give derived image variants a **20-day TTL, saving nearly 4 TB of storage per day** at its scale ([High Scalability](http://highscalability.com/blog/recommend/35665769)); the same source's "3,000 images per second (200 GB)" figure is internally ambiguous and cannot be converted to bytes per image.

| Media cost anchor, late 2026 list prices | Per TB-month |
|---|---|
| S3 Standard storage | ~$23 ([Amazon S3 Pricing](https://aws.amazon.com/s3/pricing/)) |
| S3 Glacier Deep Archive | ~$1 ([Amazon S3 Pricing](https://aws.amazon.com/s3/pricing/)) |
| Cloudflare R2 Standard, zero egress | $15 ([Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/index.md)) |
| CloudFront US/Europe egress, first 10 TB | ~$85 ([FactualMinds calculator](https://www.factualminds.com/tools/aws-cloudfront-pricing-calculator/)) |
| S3 internet egress, US East, first 10 TB | ~$90 ([Amnic](https://amnic.com); [Eon](https://www.eon.io)) |

AWS now also sells CloudFront as flat-rate plans with no overage — **Pro at $15/month for 50 TB transfer and 10M requests**, Business at $200/month for 125M requests ([Amazon CloudFront Pricing](https://aws.amazon.com/cloudfront/pricing/)) — which caps the worst-case CDN bill for a small team. Note the asymmetry: the official S3 page lists storage tiers and durability (99.999999999%) but the **per-GB egress figures above come from third-party trackers**, so verify them against a current AWS quote. Egress, not stored bytes, dominates: at 10 TB/month the R2-versus-S3 difference is roughly **$900/month** ([Cloudflare R2 calculator](https://r2-calculator.cloudflare.com/)). At 1M DAU, if 10% of ~2M daily posts carried one 200 KB image, that is ~40 GB/day raw and ~44 TB/year of derivatives — two orders of magnitude above the text data, arithmetic rather than a published 1M-DAU estimate.

Asynchronous processing belongs on a durable log. Twitter runs "one of the largest Kafka fleets in the world" ([Confluent](https://www.confluent.io)), and the documented reliability kit is a **transactional outbox** (database write and event publish atomically), idempotent consumers, staged retry topics escalating **main → retry-1 → retry-5 → DLQ**, and worker autoscaling on queue depth ([dotnet-kafka reference](https://github.com/dotnet-simformsolutions/dotnet-kafka-event-driven-architecture); [The HLD Handbook](https://hld.handbook.academy/curriculum/case-studies/photo-sharing/)). Publishing must never depend on fan-out completing. SQS pricing of **~$0.40 per million requests** makes the queue bill trivial at this scale, so choose on replay and ordering needs, not price ([AceMQ](https://acemq.com)).

Geography is the last and clearest constraint. A single US-East deployment imposes **75 ms RTT on London, 150 ms on Tokyo and 200 ms on Sydney users against ~10 ms locally**, "an order of magnitude above the local-region floor", and delays compound across sequential cross-region calls ([Harvard CS249r Vol. 2, Table 10.23](https://harvard-edge.github.io/cs249r_book_dev/vol2/assets/downloads/Machine-Learning-Systems-Vol2.pdf)). AWS names "serving a global audience from a single Region without edge caching or acceleration" an anti-pattern and warns against assuming proximity equals low latency — measure candidate regions, because routing can make a farther region faster ([AWS Well-Architected PERF04-BP06](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf04-bp06.md)). The cheapest correct shape is therefore **one write region plus multi-region reads and edge-terminated CDN**: Instagram accepts a **60 ms cross-region latency penalty on writes** while serving reads near users ([The HLD Handbook](https://hld.handbook.academy/curriculum/case-studies/photo-sharing/)). Data-residency law, not physics, may decide which regions are permissible.

## Reliability, abuse and privacy duties cost less to build before the traffic arrives

The operating baseline in the sources is a small number of user-facing SLOs with error budgets, structured logs carrying a request ID, distributed tracing across client, compute and storage, synthetic canaries, and alerts on **SLO burn rather than raw thresholds**. A **99.9% SLO allows 43.8 minutes of downtime per month**, the most common target, and the five SLI categories prescribed are availability, latency (p50/p95/p99), throughput, error rate and durability ([incident.io](https://incident.io/blog/slo-sla-sli)). Multi-window, multi-burn-rate alerting — a long window paired with a short one — is the recommended form ([Grafana Labs](https://grafana.com/blog/how-to-implement-multi-window-multi-burn-rate-alerts-with-grafana-cloud/)), and Twitter is described as running SLOs and error budgets as its reliability basis ([Blameless](https://www.blameless.com/blog-categories/reliability-and-availability)). AWS lists tracing only some components and adding tracing after an incident as anti-patterns ([AWS Well-Architected REL06-BP07](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel06-bp07.md)).

Two public postmortems show the failure that actually hurts: monitoring that shares fate with the system. Roblox's **73-hour outage** for a service with 50 million daily players began with a Consul streaming feature under high load plus a BoltDB pathology, and critical monitoring "depended on the affected systems … which severely hampered the triage process" ([Roblox newsroom](https://about.roblox.com/nl/newsroom/2022/01/roblox-return-to-service-10-28-10-31-2021)). Facebook's 4 October 2021 outage lost DNS and both normal and out-of-band network access, forcing engineers on site ([engineering.fb.com](https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/)). Build an outside-in monitor and an out-of-band access path; add cache-recovery controls (single-flight, probabilistic early expiration, cache warming) so a cold cache cannot stampede the primary, and run failover game days. Cache stampede and hot shards appear in the sources as documented risks with prescribed mitigations, not as named public postmortems; hot shards are treated as a sharded-stage (~10M users) concern ([semicolony.dev](https://semicolony.dev/codex/system-design/playbook/scale-to-millions-on-aws)).

Abuse defences are layered and measured. X's API enforces per-endpoint limits on **15-minute windows** with separate per-user and per-app quotas, `x-rate-limit-*` headers and documented `429` / error code 88 behaviour ([docs.x.com](https://docs.x.com/fundamentals/rate-limits)); its 2023 read caps of **600 posts/day for unverified, 6,000 for verified and 300 for new accounts** (later 800/8,000/400), justified as anti-scraping, drew the objection that it penalises the heaviest users and ad revenue ([Evening Standard](https://app.standard.co.uk/news/tech/twitter-elon-musk-ceo-spacex-tesla-b1091528.html)). Reddit reports blocking **23 million spam views per day**, ~25,000 net new spammy posts and comments caught daily, nearly 2 million inauthentic votes revoked daily, spam exposure cut ~20% quarter-on-quarter, and detection-to-enforcement time on hateful content falling from hours to **under five seconds** with enforcement up more than 200% ([redditinc.com](https://redditinc.com/news/how-were-keeping-reddit-real-and-safe-in-the-ai-era)). Bot-share estimates conflict by method — **35.6% of HTTP requests versus 23.44%** in another tracker and a disputed ">50%" claim — so plan for a material non-human share without trusting any single figure ([heise](https://www.heise.de/en/news/The-internet-will-soon-belong-to-bots-according-to-Cloudflare-11403115.html)).

Legal duties follow the users. GDPR Article 3(2) applies to a non-EU controller that offers services to, or monitors, people in the EU ([Regulation (EU) 2016/679, Article 3](https://www.legislation.gov.uk/eur/2016/679/article/3)), and Meta's **€1.2 billion fine with a formal suspension order** over EU-to-US transfers shows that region choice is a legal decision, not a latency one ([TechCrunch](https://techcrunch.com/2023/05/22/facebook-eu-us-data-flows-decision/)). The Digital Services Act has applied to all online intermediaries in the EU since **17 February 2024**, requiring content flagging, statements of reasons for moderation decisions, a complaint mechanism, an annual transparency report and a point of contact; only platforms above **45 million average monthly EU users** become VLOPs subject to audits and systemic-risk assessment ([European Commission](https://ec.europa.eu/commission/presscorner/detail/es/ip_24_881); [VLOP designations](https://digital-strategy.ec.europa.eu/en/policies/dsa-vlops)). A 1M-DAU app is almost certainly an "online platform" but far below the VLOP tier, so build notice-and-action tooling and an appeals queue, not an audit programme. Secondary trackers also describe Russia's 152-FZ requiring local storage of citizens' data and India's DPDP Act constraining transfers to notified countries ([adsovereign.com](https://adsovereign.com); [Databunker](https://docs.databunker.org)) — these rest on secondary sources and need counsel.

Running cost is dominated by managed services and observability, not compute. A stage-by-stage AWS walkthrough prices **~1M users at about $25,000/month** for ALB → autoscaling group → RDS → ElastiCache → SQS → S3/CloudFront with WAF in three AZs, versus $3,000 at 100K and $200,000 at 10M, and names the database as the bottleneck ([semicolony.dev](https://semicolonmy.dev/codex/system-design/playbook/scale-to-millions-on-aws)); an independent benchmark of **$0.01–$0.10 per user per month, $30,000 as a lean target**, brackets the same range ([SpendArk](https://spendark.com/blog/cloud-cost-per-user/)). Sizing confirms compute is trivial: 1M DAU at 20 requests each is **231 req/s average and 463 req/s at 2× peak**, served by three `m7g.medium` instances for about **$89/month** ([systemdesignsim.com](https://systemdesignsim.com/learn/how-many-users-can-a-server-handle)). Logging is the sleeper: Datadog is quoted at **$180K–$280K/year at 10 GB/day** and $700K–$1.1M at 50 GB/day, with list pricing of $0.10/GB ingested plus $1.70 per million events indexed ([VendorBenchmark](https://vendorbenchmark.com)) — sample, tier retention and cap cardinality from day one. Managed premiums are modest at this size: RDS runs **~1.7× the EC2 price and Aurora ~2.3×**, a three-node gap of about $360/month, "real money across fifty clusters, noise at one" ([ajayk.sh](https://ajayk.sh/blog/running-databases-on-kubernetes-2026/)); the rule of thumb is to self-host only when the managed fee exceeds **2× the engineer cost to run it** ([managed-services.md](https://github.com/zeroes-ones/Skills/blob/main/skills/07-devops/devops-engineer/references/managed-services.md)). Percona's TCO study puts the DBaaS markup at **~103%** over equivalent self-managed resources ([Percona](https://experience.percona.com)), and X's reported AWS spend of **~$7.73 million per month** illustrates that cloud-exit economics only exist two orders of magnitude above this workload ([CloudZero](https://www.cloudzero.com/blog/how-much-does-twitter-spend-on-aws-and-google-cloud/)).

## A six-phase roadmap, with sharding and multi-region deliberately last

GitHub's account is the clearest published ordering and maps directly onto this product: a Rails app on a single MySQL database, then separate databases per feature, then read replicas "to spread the load", then **ProxySQL to reduce connections against the primary**, then virtual schema domains enforced by SQL linters, then physical partitioning — which cut load on the former single cluster by **50%** across 50+ clusters and 1,200+ hosts — and only then Vitess sharding for domains that outgrew a single primary ([GitHub](https://github.blog/engineering/partitioning-githubs-relational-databases-scale/); [GitHub](https://github.blog/engineering/upgrading-github-com-to-mysql-8-0/)). Its prerequisite claim is explicit: tables must be "separated virtually in the application layer" before they can be moved physically.

| Phase | Change | Trigger to start | Evidence it must come first |
|---|---|---|---|
| 1 | Connection pooler (ProxySQL or managed), pooled app connections, query timeouts | Concurrency approaching a few hundred | `max_connections` default 151 ([MySQL manual](https://dev.mysql.com/doc/refman/8.0/en/too-many-connections.html)); GitHub adopted ProxySQL third ([GitHub](https://github.blog/engineering/partitioning-githubs-relational-databases-scale/)) |
| 2 | Materialised timeline cache (post IDs in Redis) + read replica | Timeline p99 or replica lag | Twitter's 800-entry Redis timelines ([High Scalability](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/)) |
| 3 | Media to object storage via pre-signed URLs, derivative workers, CDN + origin shield | First image or video upload | Upload must not touch app bytes ([HLD Handbook](https://hld.handbook.academy/curriculum/case-studies/photo-sharing/)) |
| 4 | Queue + transactional outbox for fan-out, notifications, moderation, search indexing | Any user-facing write doing fan-out inline | Outbox prevents message loss ([reference implementation](https://github.com/dotnet-simformsolutions/dotnet-kafka-event-driven-architecture)) |
| 5 | Split schemas by domain (users, posts, follows, media); add shard key column early | Cross-domain joins or a hot table | Shopify: backfill "may take longer than expected" ([Shopify](https://shopify.engineering/horizontally-scaling-the-rails-backend-of-shop-app-with-vitess)) |
| 6 | Shard one domain by `user_id`; add a second read region | One domain measurably outgrows one primary | Slack took 2017–2020 ([Slack](https://slack.engineering/scaling-datastores-at-slack-with-vitess/)) |

Two warnings temper the plan. First, the load may never justify phases 5–6 on its own: Stack Overflow served **209,420,973 HTTP requests/day (~2,423 req/s) and 504,816,843 SQL queries/day on four SQL Server machines** with caching and a conventional relational database, orders of magnitude above a 1M-request-per-day app ([Stack Overflow Blog, 2016](https://stackoverflow.blog/2016/02/17/stack-overflow-the-architecture-2016-edition)). A single primary with a pooler, a cache and replicas plausibly carries 1M DAU. Second, premature distribution is expensive in ways small teams cannot absorb: Segment adopted microservices "as a best practice early-on" and found "our velocity plummeted, our defect rate exploded" with three full-time engineers keeping the system alive before consolidating back to one service ([Twilio Segment](https://www.twilio.com/en-us/blog/developers/best-practices/goodbye-microservices)).

What cannot be deferred is measurement. No source states a numeric QPS, table-size or connection threshold at which to adopt caching, replication or sharding; the only triggers are qualitative ("outgrew the single-primary cluster") or vendor guidance (partition above 1 TB) ([MySQL 8.0 Reference Manual, 10.4.6](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/table-size-limit.html)). Instrument requests per user action, the read/write split per endpoint, and the diurnal peak factor in the first month, then set phase triggers from those numbers rather than from round user counts.

## Conclusion

The architecture that reaches 1M DAU is not a NoSQL rewrite; it is the current MySQL schema with three things bolted on in order — a pooler that stops connection churn, a materialised timeline cache with a read replica behind it, and an object-storage-plus-CDN path for media decoupled from the post write. Those three changes address the documented failure modes (connection exhaustion, per-follower read amplification, and media blowup) at a cost that stays inside the $10K–$30K/month band the independent estimators agree on, and they leave sharding available as a later, single-domain operation rather than an emergency.

The decisions that are genuinely irreversible should be taken now, while the schema is small: put a `user_id`-style shard key on every table and forbid cross-shard transactions and cross-domain joins in code review; store media handles, never blobs; give every write an idempotency key and an outbox event; and choose a primary write region plus an EU read region early, because GDPR transfer exposure and data-residency rules constrain region choice more tightly than latency does. The remaining uncertainty is quantitative rather than architectural: peak factor, per-follower fan-out amplification and media egress at this specific product are unmeasured in any published source, and the first month of real traffic is the only instrument that resolves them.
