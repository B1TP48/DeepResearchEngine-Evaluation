# Scaling a Twitter-like app past one database

A Twitter-like app with about one million daily active users (DAU) is a moderate system, not a hyperscale one, and its first necessary changes are about reliability, not raw capacity. Scaling Twitter's 2012–2013 figures linearly to one million users suggests roughly 2,000 timeline reads and 40 writes per second on average, which is an estimate and not a measurement. One well-tuned primary MySQL server with a tested replica can plausibly handle that, so the urgent gap is the single local database with no tested failover or backups. The changes the evidence supports as necessary are: a replicated or managed MySQL setup with tested backups and a rehearsed failover; a Redis-style timeline cache filled by an asynchronous fan-out worker; a CDN for media; per-account rate limits; and password hashing, consent and deletion processes that match the law where you serve the EU. Sharding, multi-region writes and a move to NoSQL are not necessary at this size on the evidence, though they should be planned. Cost is the least certain part: vendor estimates put a one-million-user cloud bill between about $5,000 and $30,000 a month, excluding staff.

## Terms and what the load figures measure

**Daily active users (DAU)** is the count of distinct users who use the service on a given day. The Twitter figures are not labelled consistently: one [Taoste summary of Twitter's timeline talk](https://taoste.github.io/dirtysalt/html/blogs/timeline-at-scale-in-twitter.html) calls the 150M figure DAU, while [High Scalability](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/) calls it worldwide active users. **Queries per second (QPS)** counts requests the database or service handles each second; Twitter's 2013 timeline load was about **300K QPS**, per the [High Scalability](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/) report. **Fan-out** is the step of copying one post into every follower's timeline; [Better Engineers](https://betterengineers.substack.com/p/why-lady-gagas-tweets-broke-twitters) describes fan-out on write as pushing each post into follower timelines in Redis, so reading a timeline is one lookup.

## Load and first bottlenecks

The best published load data is Twitter's, and it is old. [Balaji Devarajan's 2013 summary](https://balajidevarajan.wordpress.com/2013/08/06/twitter-architecture-for-high-scalability/) reports about 300K QPS of timeline reads against about 6,000 writes per second, a read-to-write ratio of roughly **50:1**. [High Scalability](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/) reports **400M tweets per day** and about **30 billion timeline deliveries per day**, which works out to about 75 deliveries per tweet on average. No source gives request rates for a service of exactly one million DAU, and the Twitter figures do not separate average from peak load. Scaling linearly from 150M to one million users gives my own rough figures of about 2,000 reads per second, 40 writes per second, and 2.7M tweets per day. Linear scaling ignores how real users behave, so these are planning numbers only.

The first points of failure follow from that shape of load. Reads are the bulk of the traffic, so timeline generation is the first thing to move off the database. The published operator accounts name the same early constraints. Pinterest's team says [MySQL does not scale horizontally out of the box](https://blog.bytebytego.com/p/how-pinterest-scaled-its-architecture), and Slack's [engineering post on a query incident](https://slack.engineering/the-query-strikes-again/) reports that one shard's replication lag grew under high request volume and that heavy writes exhausted memory until the kernel killed MySQL. Connection limits are a common first wall: a [Mydbops post-mortem](https://www.mydbops.com/blog/single-replica-crash-outage-postmortem) describes slow queries on a struggling replica holding pooled connections until requests backed up. Replication lag is also easy to misread, because [Code With Karani](https://www.codewithkarani.com/blog/mysql-seconds-behind-master-lies-replication-lag) notes that Seconds_Behind_Source can read zero while replication is broken, so a heartbeat table is the better check.

Global users spread the load across time zones, but the evidence on how much is thin. No social-platform engineering report quantifies how multi-region use changed peak load. The sources that discuss peaks describe surges arriving in waves across regions, which suggests capacity should be sized for overlapping regional evening windows rather than one global hour. That is an inference and should be verified with your own traffic logs.

## Data storage and the follow graph

Follow relations can stay relational. The sources describe a tweets table and a follower-to-followee table with a reverse index for fan-out, as in [DEV Community's Twitter design walkthrough](https://dev.to/gowthampotureddi/design-twitter-x-the-timeline-system-design-interview-walkthrough-145h). Timelines are a separate concern that the sources usually place in a cache. The most common pattern is a precomputed home timeline of tweet IDs in Redis, with the tweet body fetched separately. The **800-entry cap** on each timeline and the three-way Redis replication appear in [DEV Community's fan-out article](https://dev.to/gabrielanhaia/twitters-fanout-strategy-at-scale-the-trade-off-most-designs-miss-55oa), and a hybrid model switches celebrity accounts to read-time merging. These details come from secondary sites, and no primary Twitter source was found for them.

The celebrity threshold is disputed. [Syssimulator](https://syssimulator.com/learn/design-twitter-system) puts the fan-out-on-read cut-off at about **10,000 followers**, [systemdesinghq.in](https://www.systemdesinghq.in/blog/twitter-feed) says over **100,000**, and [Roundz](https://roundz.ai/blog/system-design-twitter) describes fan-out on write for accounts under about **1M** followers. For a service of your size, the threshold matters only if some accounts have very large audiences, which you should measure before choosing a figure.

On the question of relational versus NoSQL stores, the sources disagree on the store, not on the feed pattern. Discord moved its message store from Cassandra to ScyllaDB; [InfoQ](https://www.infoq.com/news/2023/06/discord-cassandra-scylladb/) reports the cluster shrank from **177 Cassandra nodes to 72 ScyllaDB nodes**. That case is append-heavy message storage read by channel, and it does not show that a follow graph has the same shape. Slack, by contrast, chose to shard MySQL through Vitess, and a [secondary Medium summary](https://medium.com/@ajaykrupalk/how-does-slack-handle-millions-of-messages-0fb068028df2) says much of its tooling depended on MySQL queries. Instagram ran Postgres with logical shards from the start. Since no controlled benchmark compares these stores on a feed workload, the evidence supports keeping accounts and follows in MySQL and putting timelines in a cache.

Sharding is needed later, and the sources give no user count that triggers it. [Instagram reached about 30 million users by 2012](https://planetscale.com/blog/the-history-of-postgres-sharding), when a single Postgres instance could no longer hold the data, and it mapped thousands of logical shards onto a few physical databases. One [OneUptime guide](https://oneuptime.com/blog/post/2026-03-31-mysql-vs-vitess-scaling-mysql-horizontally/view) gives a rule of thumb that a single MySQL node under 1 TB needs no Vitess. Slack's sharding began with one MySQL shard per workspace and moved to Vitess, and its own [engineering post](https://slack.engineering/scaling-datastores-at-slack-with-vitess/) says the hard work was choosing sharding keys, retrofitting the application and changing operations. Slack's [2.3 million queries per second](https://simonwillison.net/2020/Dec/1/scaling-datastores-slack-vitess/) peak is far above a one-million-DAU service, so it shows what Vitess can carry, not what you need.

## Application architecture and hosting

A small split is a stateless web and API tier behind a load balancer, a queue, and a fan-out worker pool that writes tweet IDs into the timeline cache. Twitter's 2012 [QCon slides](https://qconsf.com/sf2012/dl/qcon-sanfran-2012/slides/RaffiKrikorian_TimelinesAtScale.pdf) list a write API, a fan-out stage, a Redis timeline cache and batch and push compute as separate parts, and say fan-out "can be really slow", which is why it sits off the request path. Interview-prep sites describe Kafka as the queue, but no Twitter primary source confirms that. The worker pool is a deployment choice, so the team need not split into microservices to get it.

Whether to split into services is disputed, and the dispute is mostly about team size. Several 2026 guides, such as [Bitloops](https://bitloops.com/resources/software-architecture/monolith-vs-microservices), recommend a modular monolith for small teams with services extracted when a measured need appears. The opposing evidence comes from much larger organisations: Twitter [moved off Ruby](https://www.theregister.com/2012/11/08/twitter_epic_traffic_saved_by_java/) after its Ruby message queue "hit a wall", and [Airbnb's migration](https://www.infoq.com/news/2019/02/airbnb-monolith-migration-soa/) ran a phased move that compared old and new behaviour until the new services carried all the load. The "microservices cost 30–50% more" figure appears in several guides, but none cites a source, so it should not drive the decision. My synthesis is that a modular monolith with the fan-out workers, media handling and timeline cache as separate deployable processes fits a small team best.

Content delivery networks are a clear necessary change for media. [Gcore](https://gcore.com/learning/what-is-cdn-caching) explains that CDNs store images, video, JavaScript, CSS and HTML at edge servers, and reports cache hit ratios above 90% for static content, a vendor claim. [edge.network](https://edge.network/academy/video-cdn-setup) suggests a one-year cache for static assets and a short TTL or bypass for API responses. Timelines are personalised and rarely shared, so the CDN helps images, video segments, avatars and versioned web bundles much more than timeline requests.

For hosting, managed services are the most documented route for a small team. [Aurora MySQL](https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-aurora-mysql-database-clusters-256-tib-storage/) supports cluster storage of up to **256 TiB** in all regions where Aurora MySQL is offered, and an [Aurora cluster can have up to 15 replicas](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Replication.html) that share storage with the primary. Sources disagree on RDS for MySQL replica limits: one [comparison on Medium](https://medium.com/@mydbopsdatabasemanagement/aws-mysql-performance-compared-rds-aurora-and-aurora-serverless-v2-2277c02cfae2) says 15 replicas in the same region, while an [older Wikipedia summary](https://en.wikipedia.org/wiki/Amazon_Relational_Database_Service) says five. The AWS-hosted sources are more current, so the higher figure is likelier, but it should be checked against current AWS documentation. [PlanetScale](https://compass.reasonableproduct.com/saas/planetscale) offers Vitess-based pricing that is resource-based, but aggregators disagree sharply: one lists a PS-5 node at $5 a month, another lists Vitess plans from $39 a month, and a third lists a Metal plan from $609 a month. Budget from the vendor's own page, not from these aggregators.

## Reliability, security and legal duties

Failover is where small teams most often get hurt. No operator of a one-million-DAU Twitter-like app describes its failover, but larger MySQL operators show the risks. [GitHub's October 2018 incident](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/) began when a 43-second network partition led its Orchestrator tool to promote West Coast MySQL primaries; a few seconds of East Coast writes had not replicated, so those primaries could not be failed back safely. The reported result was **24 hours and 11 minutes** of degraded service and about 200,000 dropped webhook payloads, per [postmortems.app](https://postmortems.app/postmortem/4da4ac8a-fb93-426e-9ae7-eb088f115959). GitHub's fix was to stop Orchestrator promoting primaries across regions, which tells a small team that automatic cross-region promotion on asynchronous replication is dangerous. MySQL [replication is asynchronous by default](https://dev.mysql.com/doc/en/replication.html), and [semisynchronous replication](https://dev.mysql.com/doc/refman/9.7/en/replication-semisync.html) makes the source wait for a replica acknowledgement but still allows fallback to asynchronous operation.

The GitLab 2017 PostgreSQL incident shows the other side: backups that were never tested. According to [GitLab's postmortem](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/), modifications made in a window on 31 January were lost, and a [postmortem.io mirror](https://postmortem.io/incidents/gitlab--2017-01-31--database-outage-postmortem/) reports that disk snapshots were not enabled and that the pg_dump backups were not working, so restoring took over 18 hours. The [Downtime Project summary](https://downtimeproject.com/podcast/gitlabs-2017-postgres-outage/) gives about six hours of lost writes. Managed multi-AZ failover reduces this risk but does not cover a full region failure: a [secondary AWS summary](https://awsglossary.org/terms/rds-multi-az) says RDS Multi-AZ covers failover within one region, and a [Jayendra Patil summary](https://jayendrapatil.com/rds-multi-az-deployment/) gives typical instance failover of 60–120 seconds, a third-party figure. Restore testing is widely recommended: a [Digital Bridge guide](https://digitalbridge.com.tr/en/blog/backup-restore-testing.html) suggests quarterly database restores and an annual full disaster-recovery drill.

Data protection is a necessary duty where you serve the EU. The statutory text of [GDPR Article 8](https://www.gdpr.org/regulation/article-8.html) sets a default age of 16 for consent to information society services, lets member states lower it, and bars going below 13. [rgpd.com's copy of Article 8](https://rgpd.com/gdpr/chapter-2-principles/article-8-conditions-applicable-to-childs-consent-in-relation-to-information-society-services) agrees and says under-16 users need parental consent. [Captain Compliance](https://captaincompliance.com/education/gdpr-k-compliance/) states the age as fixed at under 13, which conflicts with the statute. This report follows the statutory text, because it is the primary source and the secondary summary contradicts it; the evidence does not show which national age applies to your users, so an age gate should use the age of the country where each user is.

Erasure is also required. [Article 17 erasure](https://www.chameleon-data.com/learn/gdpr-right-to-erasure) has a one-month response window, extendable for complex requests, and a [secondary summary of ICO guidance](https://getsecureslate.com/blog/gdpr-right-to-erasure) says erasure must reach backups. Deleted accounts can return if an old backup is restored, so the deletion job should also purge backups or document a retention window. No source covers non-EU regimes or size-based exemptions for small operators.

For authentication, [NIST SP 800-63B-4](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-63b-4.pdf) favours length over composition rules, with breached-password checks, rate limiting and salted hashes. Sources disagree on the length: the [draft](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-63B-4.2pd.pdf) says verifiers should require at least 15 characters, and [Netwrix](https://netwrix.com/en/resources/blog/nist-password-guidelines/) says the same. On algorithms, [passwork.pro](https://passwork.pro/blog/nist-password-guidelines-2026-what-sp-800-63b-4-requires/) says NIST no longer names them, while [CaptainDNS](https://www.captaindns.com/en/blog/nist-2025-password-recommendations) lists bcrypt, scrypt, Argon2id and PBKDF2. Use Argon2id or bcrypt with a per-user salt and store the algorithm and cost parameters with each hash.

Rate limits need care because false positives are measurable. An [NDSS spam-blacklist study](https://faculty.cc.gatech.edu/~mbailey/publications/ndss10_final.pdf) reports false-positive rates from 0.2% to 9.5% across the blacklists it tested, and a [follow-spam study](https://arxiv.org/pdf/1605.00448) reports a reference method that flagged 9.9% of legitimate users at a 10% detection threshold. These figures are from older or non-social settings, but they suggest per-account, adjustable limits with a monitored false-positive rate. No Twitter-like operator's published limits were found.

Monitoring evidence is thin. No source describes a small team's alerting or service-level targets. Replica lag and slow-query metrics are the database signals most tied to slow timelines in the material, which is an inference, not an operator finding.

## Migration path and cost by stage

The documented order of steps is consistent across sources. Mastodon's team argued it was [cheaper to buy a larger database machine](https://github.com/mastodon/blog/blob/master/content/posts/2017-04-12_Scaling-Mastodon.md) than to shard, and its [documentation](https://docs-p.joinmastodon.org/admin/scaling/) recommends pgBouncer-style pooling with reads on a replica. Instagram's [Oxyconit summary](https://blog.oxyconit.com/how-instagram-scaled-postgres-to-2-billion-users/) lists a pooler, read replicas, moving side data out, fixing heavy queries and partitioning by time before sharding. The stage ladder below combines these with the cost estimates; the user thresholds are not sourced for a Twitter-like service.

| Stage | Trigger | Change | Cost evidence |
|---|---|---|---|
| 1. Now | One local server, no tested backups | Managed MySQL, tested backups and restores, pooling | A managed database for a few thousand users runs [about $50 a month for a small instance](https://www.nightsongcloud.com/gcp-cheap-database) |
| 2. Growth | Timeline reads dominate | Redis timeline cache, async fan-out workers, CDN for media, one replica | [Kanopy](https://kanopylabs.com/blog/how-much-does-it-cost-to-build-a-social-media-app) puts launch at $500–1,500 a month |
| 3. Around 1M DAU | Large follower counts or write spikes | Feed design review, possible sharding, multi-AZ failover | [Kanopy](https://kanopylabs.com/blog/how-much-does-it-cost-to-build-a-social-media-app) gives $10,000–30,000 a month at one million users, depending on media |
| 4. Global | Users far from the write region | Read replicas per region, one write region | Cross-region writes add latency; see below |

The cost estimates disagree. [Kanopy](https://kanopylabs.com/blog/how-much-does-it-cost-to-build-a-social-media-app) gives $3,000–8,000 a month at 100,000 users, while [Dojo Business](https://dojobusiness.com/blogs/news/social-network-startup-costs) gives $8,000–30,000 at that size. A [third estimate](https://dojobusiness.com/blogs/news/social-network-profitability) gives $5,000–15,000 per million DAU, dated 2025. Taken together, a cloud budget of roughly $5,000–30,000 a month at one million users is the defensible range, and it excludes staff. [dasroot](https://dasroot.net/posts/2026/01/cost-maintenance-self-hosted-social-platforms/) gives unit prices of $0.023 per GB-month for object storage and $0.09 per GB for CloudFront transfer, which makes media delivery the largest variable cost. Staff time is not quantified by any source for this scale.

Migration has known failure modes. A naive dump, load and switch [loses writes made after the dump](https://www.sg2technologies.com/resources/database-migration-pitfalls). A [game-platform post-mortem](https://lootlocker.com/blog/db-postmortem-data-loss-during-database-migration) reports that a replication process used credentials rotated earlier, so the gap was not noticed until migration day, and the source was deleted before integrity was confirmed. The safe pattern is dual writes or a replication stream, a backfill with a checkpoint, read comparison before cutover, and keeping the old database until data is verified. Slack, for example, [wrote to both old and new systems](https://betterengineers.substack.com/p/how-slack-scaled-mysql-to-23-million) during its transition. Timing is the other constraint: a [2 TB PostgreSQL migration](https://dev.to/yash_pritwani_07a77613fd6/zero-downtime-database-migration-shadow-writes-dual-read-and-the-12-second-cutover-2k33) took about 18 hours of backfill at low priority, so a database near 1 TB implies days of copying and weeks of total effort.

Multi-region writes should wait. The [AWS guidance](https://builder.aws.com/content/39DdgeXV3vTKHJ8cRUwWWGHS1is/data-management-patterns-for-multi-region-deployments-on-aws) describes a read-local, write-global pattern, in which non-primary regions pay cross-region write latency and failover causes a brief write outage, while a managed global database has typical lag under one second. Multi-writer setups need conflict handling that the sources do not address for social-graph data such as follower counts. [Veduis](https://veduis.com/blog/multi-region-architecture/) notes that multi-region deployments can produce more incidents than a well-designed single region.

## Conclusion

The necessary changes are the ones that protect data and keep reads fast, not the ones that prepare for a billion users. Move off the single local MySQL server to a managed or replicated setup, tested backups, and a rehearsed failover that stays inside one region. Put timelines in a cache filled by asynchronous workers, and send media through a CDN. Add per-account rate limits, modern password hashing, and an age gate and deletion process for EU users. Defer sharding and multi-region writes until measured write throughput, storage size or user location justify them; the sources give no user count that forces them at one million DAU.

Several figures remain uncertain and should be measured before committing budget. The Twitter load figures are from 2012–2013, the follower threshold for fan-out is disputed, and the cloud cost range is vendor-derived. The most useful next step is to measure your own read-to-write ratio, follower distribution and peak hours, then test a restore and a failover before any architecture change.
