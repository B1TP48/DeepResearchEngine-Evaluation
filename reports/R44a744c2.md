# Scale the Feed Service in Measured Stages

At 1M users per day, the service does not need a rewrite, a NoSQL store or sharding on day one. Under the stated assumptions, average load is modest: roughly 6 tweet writes per second and about 116 timeline reads per second, with peaks a few times higher. The binding constraints are read fan-out, cache hit rate, availability and geography, not data size. The necessary changes are: move to managed MySQL with replicas and a cache; adopt time-sortable IDs, bidirectional follow records and keyset pagination now; move fan-out and other slow work off the request path with a hybrid timeline; put a global front door and CDN in front of one primary region; and add SLOs, tested restores, safe schema-migration tooling and per-user rate limits. Sharding (Vitess or application-level logical shards) and NoSQL stores should wait until measured write load or data size requires them. The most useful next step is to replace the assumed traffic figures below with the product's own analytics.

## Read fan-out and cache hits, not storage size, set the early load

The load figures in this report are illustrative calculations from assumptions the sources do not establish. Assuming 0.5 tweets per daily user, 500,000 writes per day equals about 5.8 writes per second on average, with roughly 20 per second at a 3× peak. Ten timeline loads per user per day gives about 116 reads per second, and hydrating 20 tweets per page gives about 2,300 tweet reads per second on average and about 7,000 at peak. With a 90% cache hit rate, about 700 peak reads per second would reach the database. A second estimate with 0.5 posts per user and about 30 posts per second at peak reaches similar conclusions, so the order of magnitude is stable even though the inputs vary. Total tweet data is around 90 GB per year under these assumptions, which one well-provisioned MySQL primary can hold for years.

Read-side pressure is what changes the design. Meta's TAO workload is about **99.8% reads** ([Meta TAO slides, Univ. of Crete (2021)](https://www.csd.uoc.gr/~hy559/fall21/hy559-20211105-tao.pdf)), and the same pattern is expected for a timeline product. If timelines were built by pulling every followed account's tweets, an average of 150 follows per user would mean about 1.5 billion follow lookups per day, roughly 17,000 per second. That is why the follow list must be cached or materialised. Fan-out-on-write has its own multiplier: an average of 150 followers gives about 75 million timeline inserts per day, while 200 followers gives about 100 million, so the follower assumption matters. For scale context, Twitter's 2012 figures were about **150 million active users and 300,000 timeline queries per second** ([Krikorian, QCon SF 2012 slides](https://www.slideshare.net/chrisbolman1/twitter-raffi-krikoriantimelinesatscale)). Instagram began sharding Postgres when it reached **more than 25 photos and 90 likes per second** ([Engineers Codex](https://read.engineerscodex.com/p/how-instagram-scaled-to-14-million)). A 1M-DAU product sits well below both thresholds, which supports a staged approach.

## Keep MySQL and add replicas before any sharding

Every large platform in the sources kept a relational engine as its durable layer for years. The practical path is staged, with each step triggered by a measured limit rather than by anticipated growth.

| Stage | Trigger | Change | Supporting source |
|---|---|---|---|
| 1. Now | Any budget | Managed MySQL with backups and point-in-time recovery, one or two read replicas, Redis or Memcached cache, connection pooling | [AWS RDS User Guide](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html) (up to 15 replicas, created manually); [ProxySQL](https://proxysql.com/features/query-routing/) (routes reads to replicas without app changes) |
| 2. Now, while data is small | Before data grows | Snowflake-style 64-bit IDs, follows stored in both directions, keyset pagination, denormalised counts | [Haider Zdbre](https://haiderzdbre.substack.com/p/how-instagram-sharded-postgresql-with-2-engineers) (Instagram's 41-bit time, 13-bit shard, 10-bit sequence IDs) |
| 3. When one primary saturates | Sustained write load or data beyond one instance | Application-level logical shards, or Vitess | [Vitess sharding guidelines (v19)](https://vitess.io/docs/19.0/user-guides/vschema-guide/sharding-guidelines/) (the highest-QPS query should drive the sharding key) |
| 4. For one workload | A measured bottleneck | DynamoDB, Cassandra or ScyllaDB for a narrow workload such as an archive | [AWS DynamoDB docs](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html) (eventually consistent by default) |

Read replicas carry real caveats. ProxySQL-based splitting can send a read right after a write to a lagging replica, and a transaction containing a write pins its reads to the primary ([Big Iron](https://www.bigiron.cc/guides/read-write-splitting-at-the-proxy-the-pgbouncer-and-proxysql-pattern); [JusDB](https://www.jusdb.com/blog/proxysql-series-mysql-replication-read-write-split-up)). Timeline and profile views that must show a user's own new post therefore need a primary read or a cache write-through. Replicas also do nothing for write load, which is the limit that eventually forces sharding.

The schema decisions in Stage 2 are cheap now and expensive later. The proposed design, which is the analysis's own rather than a sourced template, shards tweets by author ID and keeps follows in two tables, one keyed by follower and one by followee, so that both "who do I follow" and "who follows me" are single-shard lookups. Vitess guidance supports sharing a unique vindex across related tables so that related rows land on one shard ([Vitess shared vindexes, v13 archive](https://vitess.io/docs/archive/13.0/user-guides/vschema-guide/shared-vindexes/)). TAO takes the same approach, storing associations by source object with inverse edges ([Univ. of Crete TAO deck (2023)](https://www.csd.uoc.gr/~hy559/fall23/hy559-20231018-tao.pdf)). The cost is that a follow across two shards becomes a cross-shard write. No source reviewed covers a saga or outbox pattern for it, so the team will need to design that reconciliation itself.

On NoSQL, the evidence points to caution. Twitter tried Cassandra around 2010, did not fully replace MySQL because Cassandra lacked auto-increment, and later built Manhattan ([X Engineering blog (2017)](https://blog.x.com/engineering/en_us/topics/infrastructure/2017/the-infrastructure-behind-twitter-scale)). Discord moved its messages from Cassandra to ScyllaDB and cut its largest cluster from about **177 Cassandra nodes to 72 ScyllaDB nodes** ([Medium (c. 2025)](https://medium.com/@nitishh205/how-discord-migrated-trillions-of-messages-and-why-it-was-worth-every-byte-571e4bb5211c)). Discord's latency claims conflict: one article reports a fall from **about 200 ms to 5 ms** ([The New Stack, 2023](https://thenewstack.io/how-discord-migrated-trillions-of-messages-to-scylladb/)), while another reports a p99 read falling from **40–125 ms to 15 ms** ([Medium, Machine Learning Made Simple](https://machine-learning-made-simple.medium.com/why-social-media-giant-discord-ditched-the-cassandra-database-622d50794b25)). Neither figure was checked against Discord's original post, so the direction is clear but the magnitude is not. A NoSQL store also adds a second consistency model, and Cassandra-family systems require partition-key design to avoid the hot partitions Discord hit ([Zahere](https://zahere.com/how-discord-stores-trillions-of-messages)). No source establishes a volume threshold at which MySQL must be replaced.

## A hybrid timeline inside a modular monolith

Feed delivery is where most application-level risk sits. Large platforms converge on a hybrid: ordinary accounts push post IDs into follower timelines on write, while accounts with very large follower counts are merged in at read time. Twitter's 2012 QCon material describes this shape and found naive timeline materialisation too slow at 300,000 timeline queries per second ([Krikorian slides](https://www.slideshare.net/chrisbolman1/twitter-raffi-krikoriantimelinesatscale); [High Scalability summary](https://highscalability.com/the-architecture-twitter-uses-to-deal-with-150m-active-users/)). Those slides describe the timeline cache as a Redis list of tweet IDs, updated with RPUSHX so that only timelines already in cache receive new entries ([Raffi Krikorian, Slideshare](https://www.slideshare.net/slideshow/raffi-krikorian-twitter-timelines-at-scale/24040648)). Redis sorted sets offer a comparable structure with rank and score range queries for pagination ([Redis glossary](https://redis.io/glossary/redis-sorted-sets/)).

The celebrity threshold is the most important tuning value, and the sources do not agree on it. One group of secondary guides puts the cut-off at about **10,000 followers** ([DEV, Twitter fan-out strategy](https://dev.to/gabrielanhaia/twitters-fanout-strategy-at-scale-the-trade-off-most-designs-miss-55oa); [DesignGurus](https://www.designgurus.io/blog/design-social-media-news-feed)). Another suggests a range starting at **100,000** ([CS Learning Portal](https://www.cslearningportal.com/tutorials/system-design/design-a-news-feed-in-system-design)), and a third suggests **over 1 million** ([System Design Simulator](https://systemdesignsimulator.org/designs/news-feed)). No Twitter or X figure was found in the sources reviewed. The sensible course is to make the threshold a configuration value and set it from measured fan-out queue lag. Fan-out workers should be idempotent, because at-least-once delivery is the common case, and batching around 1,000 followers per message is a tuning option ([Intervue Club](https://intervueclub.com/problems/databases/design-a-news-feed), a secondary source).

Architecturally, the evidence favours a modular monolith first. Shopify considered microservices, ruled them out because of distributed-system complexity, and chose a single deployable unit with enforced module boundaries ([InfoQ, 2019](https://www.infoq.com/news/2019/07/shopify-modular-monolith)). Its current site says it uses a modular monolith rather than microservices ([Shopify, 2026](https://www.shopify.com/enterprise/blog/ecommerce-microservices)). Amazon Prime Video's move back to a single process reported **more than 90% lower infrastructure cost**, but that was a video-quality monitoring pipeline, not a social feed, and the authors said the choice should be made case by case ([DevClass, 2023](https://www.devclass.com/ci-cd/2023/05/05/reduce-costs-by-90-by-moving-from-microservices-to-monolith-amazon-internal-case-study-raises-eyebrows/1621790)). The practical split is one app with modules for users, graph, posts, timelines and notifications, with the fan-out workers extracted first because their load profile differs most. Kafka is a reasonable durable log because it provides ordered partitions, replay and consumer groups ([Apache Kafka docs](https://kafka.apache.org/44/getting-started/introduction/)). A simpler queue is enough if only the fan-out consumer reads the events. The sources do not compare Kafka with SQS, RabbitMQ or Pub/Sub, so that choice should rest on the team's operating capacity.

## One region at the edge, with residency designed in

The sources support a single global entry point in front of one primary region, with a warm standby elsewhere. Traffic routing documentation from Cloudflare, AWS and Google was not found, so the routing advice is general. Latency figures are the stronger evidence: a third-party GCP guide gives expected round-trip times of **20–30 ms** between us-central1 and us-east1, **90–110 ms** from us-central1 to europe-west1, **140–170 ms** to asia-east1, and **200–250 ms** between europe-west1 and asia-east1 ([oneuptime](https://oneuptime.com/blog/post/2026-02-17-how-to-troubleshoot-high-latency-between-compute-engine-instances-across-regions/view)). A user in Asia hitting a US-only origin therefore pays a round trip of well over 100 ms on every request, and TLS handshakes multiply that. Edge termination matters as much as server speed. The analysis's own targets, a p95 under about 300 ms within a continent and under about 500 ms across continents, are judgement rather than sourced figures.

Database replication decides how much a second region costs. Aurora Global Database replicates at the storage layer with typical lag under one second, whereas ordinary cross-region replicas lag more ([AWS Aurora docs](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Replication.CrossRegion.html)). AWS says binlog-based replication lag "can grow indefinitely" under heavy change rates or network delay, though it is typically under a minute, and that a secondary region can be promoted in under a minute ([AWS availability FAQ](https://docs.aws.amazon.com/rds/latest/auroraextendedcontent/aurora-faq-availability-and-durability.html)). The AWS re:Invent 2020 deck describes pausing writes when lag exceeds a limit ([re:Invent deck](https://d1.awsstatic.com/events/reinvent/2020/Deep_dive_on_Global_Database_for_Amazon_Aurora_DAT404.pdf)). The sources differ on the number of secondary regions, with the documentation stating up to 10 and the 2020 deck saying up to 5, so the current limit should be checked directly. Active-active writes were not covered by any source, and for a small team they add conflict resolution that is hard to justify at this scale.

Delivery costs are driven by media. CloudFront's North America and Europe rate is **$0.085 per GB for the first 10 TB**, and Asia-Pacific rates are higher, for example **$0.120 per GB** in Hong Kong, Singapore, Korea and Taiwan ([Blazing CDN](https://blog.blazingcdn.com/en-us/cloudfront-pricing-tiers-and-free-usage); [egresscost.com](https://egresscost.com/aws/cloudfront-regions/)). These figures come from third-party sites because no official CloudFront price page was retrieved. Cloudflare's self-serve Pro plan is listed at about **$20–25 per month** ([Blazing CDN](https://blog.blazingcdn.com/en-us/cloudflare-cdn-pricing-calculator-forecast-your-traffic-costs)), with load balancing sold separately. Under the stated assumptions, Cloud Run request-based compute is roughly **$2,600–2,700 per month** before concurrency savings, using published rates of $0.000024 per vCPU-second and $0.40 per million requests ([Economize](https://www.economize.cloud/resources/gcp/pricing/cloud-run/)). CDN egress at 30 TB per month comes to about **$2,450**, and at 150 TB per month about **$10,050**, on North America and Europe list rates. Those are the scenarios to budget around.

Data residency is a legal question with conflicting inputs. GDPR Chapter V governs transfers of personal data to third countries, and the EDPB's criteria determine when processing counts as a transfer ([EDPB Guidelines 05/2021](https://www.edpb.europa.eu/system/files/2021-11/edpb_guidelinesinterplaychapterv_article3_adopted_en.pdf)). China's PIPL requires one of three routes for outbound transfers ([IAPP](https://iapp.org/news/a/top-5-operational-impacts-of-the-pipl-part-5-international-data-transfers)), but the thresholds conflict: one guide puts the security-assessment line at **1 million or more** individuals ([NHIMG](https://nhimg.org/china-pipl-guide)), another says **1 million or at least 100,000 cumulatively** ([China Policy Guide](https://chinapolicyguide.com/articles/china-data-cross-border-transfer-guide/)), and a third uses **1 million non-sensitive or 10,000 sensitive** individuals ([ChinaGateway](https://chinagateway.pro/glossary/cross-border-data-transfer.html)). The CAC's own text should decide this. India's DPDP Act, Section 16, permits transfers except to countries the government notifies as restricted, and no list had been notified as of mid-2026 ([TCSA](https://www.tcsa.in/frameworks/dpdp/cross-border-transfer)). The practical design, whatever the final legal view, is a home-region field on each account, so that residency partitions can be added later without a rewrite.

## Operations: SLOs, safe migrations and tested restores

The operational work that matters most at this scale is observability, reliability targets and a migration method that can be rolled back. For observability, the common open pattern is OpenTelemetry feeding Prometheus, Loki and Tempo, with Grafana on top ([Last9](https://last9.io/blog/opentelemetry-with-grafana/)). Managed Grafana Cloud's free tier includes 10,000 active series and 50 GB of logs per month ([CostBench](https://costbench.com/software/developer-tools/grafana/)). Its Pro pricing is contested. Most sources describe a **$19 per month platform fee** plus usage ([CloudZero](https://www.cloudzero.com/blog/grafana-cloud-pricing/)), but one page lists **$19 per user** ([CostBench](https://costbench.com/software/observability/grafana-cloud/)). Cardinality is the real cost driver: one teardown shows a single high-cardinality label moving the metrics bill from zero to about **$2,089 per month** at roughly 328,500 series ([BudgetForge](https://www.budgetforge.dev/tools/grafana-cloud-pricing-2026)). Label discipline should therefore start on day one. Self-hosting avoids licence fees but needs staff time, which for a very small team probably costs more.

Reliability targets should follow Google's SRE guidance, which treats SLOs as the central tool and uses an error budget to govern releases ([Google SRE workbook, Implementing SLOs](https://sre.google/workbook/implementing-slos/)). No source gives a numeric target for a social platform. A starting point of **99.9% monthly availability** on timeline reads and writes, plus an overload measure for rate-limited responses, is a reasonable assumption to measure against. Backups matter only when restores are tested. Google's data-integrity chapter emphasises restores over backups, and advises retaining backups long enough to cover at least a week or two of releases ([Google SRE, Data Integrity](https://landing.google.com/sre/sre-book/chapters/data-integrity/)). Privacy rules can also require hard deletion, which limits retention. Restore drills into an isolated environment, with checks on row counts and business invariants, are the real disaster-recovery test.

For security, the OWASP API Security Top 10 (2023) is the current list. Its top risk is Broken Object Level Authorization, where an endpoint returns an object without checking the caller's rights ([Safeguard](https://safeguard.sh/resources/blog/owasp-api-top-10-2023)). The list also covers Unrestricted Resource Consumption (API4) and Unrestricted Access to Sensitive Business Flows (API6) ([Salt Security](https://salt.security/blog/owasp-api-security-top-10-explained)), which together describe the spam and bot risks for posting and following. Every post, follow and profile endpoint should check ownership server-side, with cross-user tests in CI, and rate limits should apply per account, per IP and per endpoint at the gateway. The sources did not cover TLS, session management, secrets handling, DDoS protection or spam detection, so those controls rest on general practice rather than evidence.

For schema changes on the live MySQL, gh-ost is the stronger option. It is triggerless, can be paused, and is tested continuously on replicas that serve no traffic ([gh-ost README](https://github.com/github/gh-ost/blob/master/README.md)). Recent releases add checkpoints and a `--panic-on-warnings` option ([gh-ost releases](https://github.com/github/gh-ost/releases)). By contrast, pt-online-schema-change copies rows with INSERT IGNORE, so a duplicate-key row can be dropped silently, and it cannot be used on tables that already have triggers ([Debian manpage](https://manpages.debian.org/unstable/percona-toolkit/pt-online-schema-change.1p); [Liquibase](https://contribute.liquibase.com/extensions-integrations/directory/database-tutorials/percona/percona-toolkit/)). Moving to a new architecture needs a staged sequence: deploy code that reads both schemas, backfill in throttled batches, dual-write and compare, switch reads, then retire the old path. Discord's guidance matches this, keeping the old store as source of truth until reads are validated and migrating its riskiest data last ([Dev.to](https://dev.to/techlogstack/how-discord-migrated-trillions-of-messages-and-fired-their-garbage-collector-4818)). The sources did not cover the dual-write mechanics in detail. For load testing, k6 supports open arrival-rate models and SLO-style thresholds, which suit a requests-per-second target ([Grafana k6](https://grafana.com/oss/k6/); [k6 repository](https://github.com/grafana/k6)). Its open-source edition does not distribute a run natively, so large tests need execution segments or the Kubernetes operator ([k6 docs](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/)). The test should run against production-sized data, since an empty database hides the bottlenecks that matter.

## Conclusion

The central implication is sequencing. The team should spend its first effort on the changes that are cheap now and costly later: managed MySQL with replicas and a cache, time-sortable IDs, two-way follow records, keyset pagination, an explicit user-ID shard key and a per-user home region. Those choices keep the sharding and residency options open without adding operational weight. The feed path deserves the next investment, because fan-out and cache design determine read latency long before storage does. A hybrid timeline with a configurable threshold, asynchronous workers and idempotent consumers is the change most likely to protect the product during growth spikes.

Several decisions should wait for evidence. Sharding, Vitess and NoSQL should be triggered by measured write saturation, replica lag or data size rather than by the assumed numbers in this report. A second region should follow measured latency complaints or a disaster-recovery requirement. Legal review must settle which residency rules apply before any user region is launched, particularly China, where the sources give conflicting thresholds. The largest unknowns are the follower distribution, the peak-to-average ratio and the media share of traffic, and the team should measure all three before committing to a threshold, a cache size or a CDN contract.
