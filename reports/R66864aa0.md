# Scale the Social App Safely Worldwide

For planning, define **one million users per day as one million distinct accounts completing a meaningful action in a stated 24-hour window**; track sessions and API requests separately, because daily users alone do not determine capacity. Measure request rate in requests per second (QPS), and define service-level objectives (SLOs) as targets against user-facing indicators such as latency, errors, and availability; define recovery time objective (RTO) as the time to restore service and recovery point objective (RPO) as the tolerable data-loss window ([Google SRE, “Service Level Objectives”](https://sre.google/sre-book/service-level-objectives/); [Google Cloud, “Architecting disaster recovery for cloud infrastructure outages”](https://docs.cloud.google.com/architecture/disaster-recovery?hl=en)). The recommended path is to make the existing product observable, horizontally deployable, and recoverable before adopting distributed databases or a large microservices architecture. An illustrative workload can range from hundreds to thousands of average API requests per second, with substantially higher peaks, depending on user behavior and peak concentration—not on the user count alone ([Google Cloud, “Manage traffic and load for your workloads”](https://docs.cloud.google.com/architecture/infra-reliability-guide/traffic-load)). Keep MySQL initially if representative load tests show it meets the product’s objectives; add replicas, queues, or more regions only when evidence or business requirements justify them. Treat security, abuse prevention, privacy, moderation, and tested recovery as launch requirements alongside performance.

## Capacity depends on user behavior, not the daily-user label

The service needs a workload model that separates **daily active users, sessions, user-visible requests, and internal work**. For example, an explicitly illustrative scenario of one million daily active users, three sessions per user per day, and 20 feed fetches per session yields 60 million feed fetches per day, or about 694 requests per second on average; applying an assumed fivefold peak factor gives about 3,472 feed requests per second. If each user also creates two posts per day, that scenario produces two million posts daily, or about 23 average and 116 peak post requests per second. These are arithmetic scenarios, not forecasts; actual sessions, request mix, and peaks must come from product analytics and load tests ([Google Cloud, “Manage traffic and load for your workloads”](https://docs.cloud.google.com/architecture/infra-reliability-guide/traffic-load); [Google SRE, “Service Level Objectives”](https://sre.google/sre-book/service-level-objectives/)).

A different illustrative model—50–200 API requests per daily active user—implies about 580–2,315 average requests per second across the same user base, before peak multipliers. The difference from the feed-focused scenario reflects different assumptions, not a reliable forecast; capacity planning should record the assumptions rather than select one estimate as fact ([Google Cloud, “Manage traffic and load for your workloads”](https://docs.cloud.google.com/architecture/infra-reliability-guide/traffic-load)). Track per-endpoint request rate, concurrency, p50/p95/p99 latency, errors, request and response sizes, and client region. Also track product events separately—feed refreshes, pagination, posts, replies, likes, follows, searches, and media retrieval—because one user request can trigger database writes, moderation, notifications, and timeline delivery.

Timeline delivery may amplify write work. In the illustrative two-million-post scenario, assuming 200 followers per author would imply 400 million timeline-entry writes per day, or about 4,630 per second on average and 23,148 at a fivefold peak. That multiplier is only an example: follower counts and posting activity are skewed, and high-follower accounts can create disproportionate bursts. Fan-out-on-write makes common feed reads simpler but moves work to post time; fan-out-on-read avoids those writes but does more work when a user opens a feed. A hybrid—precomputing timelines for ordinary accounts while fetching selected high-follower accounts’ posts at read time—is worth testing if measurements show a need, not adopting with a fixed threshold ([Raffi Krikorian, “Real-Time Delivery Architecture at Twitter”](https://eecs.csuohio.edu/~sschung/DSA460/QConNY2012-RaffiKrikorianReal-TimeDeliveryArchitectureatTwitter.pdf); [Red Planet Labs, “How we reduced the cost of building Twitter at Twitter-scale by 100x”](https://blog.redplanetlabs.com/2023/08/15/how-we-reduced-the-cost-of-building-twitter-at-twitter-scale-by-100x/)).

Set endpoint-specific SLOs before scaling. A reasonable initial availability target to consider is **99.9% of valid core requests per month**; Google SRE’s availability table translates 99.9% to 43.2 minutes of unavailability per month, while noting that failed-operation rates can better describe partial failures ([Google SRE, “Availability Table”](https://sre.google/sre-book/availability-table/)). Define latency objectives by endpoint and percentile, and validate them against user experience from multiple regions rather than treating server processing time as worldwide end-to-end latency. A proposed starting recovery envelope is an RTO of no more than four hours and an RPO in the five-to-fifteen-minute range, subject to business approval and restore testing; tighter targets increase cost and operational complexity ([Google Cloud, “Architecting disaster recovery for cloud infrastructure outages”](https://docs.cloud.google.com/architecture/disaster-recovery?hl=en); [AWS Well-Architected, “Recovery strategies”](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel13-bp02.html)). Availability, durability, and recovery are different properties: measure them separately.

## Keep the core simple; scale each tier on evidence

Move from a local-only deployment to **multiple interchangeable, stateless application instances behind a health-checked load balancer**. Keep session and other shared state outside individual application servers so instances can be replaced or scaled independently. Use a CDN for static assets and suitable public content, but do not cache personalized timelines or account data unless authorization and cache-key behavior are demonstrably safe ([Google Cloud, “Patterns for scalable and resilient apps”](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps); [Google Cloud, “Caching overview”](https://docs.cloud.google.com/cdn/docs/caching)). A managed application platform and managed MySQL service are sensible small-team defaults if their cost, region, and reliability features fit the requirements.

Retain MySQL as the source of truth until testing shows a specific limitation. A starting relational design can keep accounts, posts, follows, and engagements in separate tables; index follows in both lookup directions and index posts for the product’s author-and-time queries. Use deterministic cursor pagination with an indexed ordering key rather than relying on deep offsets, and keep indexes limited to measured query needs because they add storage and write overhead ([MySQL Reference Manual, “Multiple-column indexes”](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html); [MySQL Reference Manual, “LIMIT query optimization”](https://dev.mysql.com/doc/refman/8.0/en/limit-optimization.html); [MySQL Reference Manual, “Optimization and Indexes”](https://dev.mysql.com/doc/refman/8.4/en/optimization-indexes.html)). Treat precomputed timelines and counters as derived data, not authoritative records. Make post creation durable before acknowledging it, and provide a read-your-writes path so users can see their own new posts even if a replica or timeline projection is behind.

Add read replicas only when measurements show read pressure is constraining the primary and the application can tolerate replica lag for the chosen queries. MySQL’s documented read-scale pattern keeps writes on the source; replication is asynchronous by default, so freshness-sensitive reads should go to the primary or use a defined consistency mechanism ([MySQL Reference Manual, “Using Replication for Scale-Out”](https://dev.mysql.com/doc/refman/26.7/en/replication-solutions-scaleout.html); [MySQL Reference Manual, “Replication FAQ”](https://dev.mysql.com/doc/refman/8.4/en/faqs-replication.html)). Partitioning can help specific table-management or query-pruning needs, but does not distribute writes across database servers and has schema restrictions ([MySQL Reference Manual, “Partitioning overview”](https://dev.mysql.com/doc/refman/8.4/en/partitioning-overview.html); [MySQL Reference Manual, “Partitioning restrictions and limitations”](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations.html)). Sharding or replacing MySQL should follow evidence of a write, data-size, hotspot, or access-pattern limit—not the one-million-user milestone. Large-platform examples show that MySQL can remain useful at scale, but also that sharding and specialized storage bring substantial operational work ([Twitter Engineering, “The Infrastructure Behind Twitter: Scale”](https://blog.x.com/en/engineering/the-infrastructure-behind-twitter-scale); [Twitter Engineering, “How We Scaled Reads On the Twitter Users Database”](https://blog.x.com/en/engineering/how-we-scaled-reads-on-the-twitter-users-database)).

Move independent, non-interactive work—such as notifications, media processing, and timeline fan-out—to durable queues when it makes requests slow or creates bursts. Queue handlers must be idempotent because tasks may be delivered more than once; monitor retries, failures, and queue age ([Google Cloud, “Understand Cloud Tasks”](https://docs.cloud.google.com/tasks/docs/dual-overview)). Keep the existing application modular rather than splitting it into many services in anticipation of scale; microservices and separate data ownership add deployment, failure-handling, and troubleshooting burdens, and are most useful when clear boundaries and independent operational needs exist ([AWS Prescriptive Guidance, “Decomposing monoliths into microservices”](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-decomposing-monoliths/); [AWS Prescriptive Guidance, “Asynchronous communication”](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-integrating-microservices/asynchronous.html)).

## Global reliability requires more than global routing

Start with a primary region near the largest user population, multi-zone resilience where available, and edge delivery for cacheable content. Add application-serving regions when measured regional latency, disaster-recovery objectives, or legal obligations justify their complexity. A global load balancer can direct traffic to nearby healthy backends, but it does not make a single-region database local worldwide or make a shared dependency resilient ([Google Cloud, “Design reliable infrastructure”](https://docs.cloud.google.com/architecture/infra-reliability-guide/design); [Google Cloud, “Best practices for Compute Engine regions selection”](https://docs.cloud.google.com/solutions/best-practices-compute-engine-region-selection)). Avoid active-active database writes until the product has an explicit consistency, conflict-resolution, and failover design; multi-region operation adds replication, latency, and data-transfer trade-offs ([AWS Prescriptive Guidance, “Multi-Region fundamental 2: Understanding the data”](https://docs.aws.amazon.com/prescriptive-guidance/latest/aws-multi-region-fundamentals/fundamental-2.html)).

Instrument user-visible latency, traffic, errors, and saturation alongside database connections, slow queries, storage and I/O, queue age, cache behavior, and replica lag. MySQL Performance Schema and slow-query logging can help identify expensive statements, waits, and rows examined; tune queries and indexes before adding infrastructure ([MySQL Reference Manual, “Performance Schema”](https://dev.mysql.com/doc/refman/8.4/en/performance-schema.html); [MySQL Reference Manual, “The Slow Query Log”](https://dev.mysql.com/doc/refman/8.4/en/slow-query-log.html)). Use dashboards, traces, and actionable alerts, and define incident ownership, escalation, runbooks, and post-incident follow-up ([Google SRE, “Monitoring Distributed Systems”](https://sre.google/sre-book/monitoring-distributed-systems/); [AWS Well-Architected, “Responding to events”](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/responding-to-events.html)). Back up data off-host, retain binary logs for point-in-time recovery where appropriate, and regularly test full restores; replication alone does not protect against replicated deletion or corruption ([MySQL Reference Manual, “Point-in-Time Recovery Using Binary Log”](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-binlog.html); [AWS Well-Architected, “Identify and back up data”](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel09-bp01.html)).

Treat authentication, authorization, abuse resistance, and moderation as core product controls. Check authorization for each requested post, account, or relationship; use adaptive password hashing, secure secret storage, least-privilege access, and phishing-resistant MFA for privileged users. Apply bounded, risk-based rate limits to costly or abuse-prone actions, rather than relying on IP address alone ([OWASP API Security Top 10](https://devguide.owasp.org/en/07-training-education/07-api-top-ten/); [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); [AWS IAM Security Best Practices](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html); [OWASP Bot Management and Anti-Automation](https://cheatsheetseries.owasp.org/cheatsheets/Bot_Management_and_Anti-Automation_Cheat_Sheet.html?trk=article-ssr-frontend-pulse_little-text-block)). Provide an accessible reporting flow and a case-management process with evidence, rationale, review, and appeal; combine automated detection with trained human judgment for ambiguous or consequential cases. Measure review backlogs, repeat abuse, appeal reversals, and false positives rather than assuming a fixed staffing ratio ([X Help Center, “Report abusive behavior”](https://help.x.com/en/safety-and-security/report-abusive-behavior); [Regulation (EU) 2022/2065, Articles 16–17](https://eur-lex.europa.eu/eli/reg/2022/2065/oj/eng/pdf); [Engineering at Meta, “Fighting Abuse @Scale”](https://engineering.fb.com/2019/12/13/security/fighting-abuse-scale-2019/)).

Worldwide availability does not mean one privacy or moderation rule applies everywhere. GDPR can apply to organizations outside the EU that offer services to people there or monitor their behavior; its international-transfer rules do not impose a general requirement to store all EU data only in the EU ([GDPR, Articles 3, 32 and 33](https://eur-lex.europa.eu/eli/reg/2016/679/oj/?pid=14006577); [European Data Protection Board, “International transfers”](https://www.edpb.europa.eu/topics/international-transfers-and-international-cooperation_ga)). Assess the DSA and UK Online Safety Act where applicable, including notice, explanation, complaint, and risk-assessment workflows; the DSA’s additional very-large-platform regime uses an EU threshold of 45 million average monthly recipients plus formal designation, not a worldwide daily-user count ([Digital Services Act, EUR-Lex](https://eur-lex.europa.eu/eli/reg/2022/2065); [Ofcom, “Illegal content duties under the Online Safety Act”](https://www.ofcom.org.uk/online-safety/illegal-and-harmful-content/illegal-content-duties-under-the-online-safety-act)). Also assess child-privacy rules, California coverage, Brazil’s transfer rules, India’s phased data-protection framework, and China’s potential localization and transfer requirements; applicability depends on users, company operations, and data practices, so regional counsel is necessary ([FTC, “COPPA FAQs”](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions); [California Privacy Protection Agency, “CCPA updates”](https://cppa.ca.gov/regulations/ccpa_updates); [Brazil ANPD, Resolution CD/ANPD No. 19](https://www.gov.br/anpd/pt-br/acesso-a-informacao/institucional/atos-normativos/regulamentacoes_anpd/resolucao-cd-anpd-no-19-de-23-de-agosto-de-2024); [India Gazette, DPDP Act commencement notification](https://www.meity.gov.in/static/uploads/2025/11/c56ceae6c383460ca69577428d36828b.pdf); [China PIPL, English text](https://en.spp.gov.cn/2021-12/29/c_948419_2.htm)). Map data, processors, retention, deletion, and regional access before choosing global storage, logging, analytics, or support arrangements.

## Migrate in reversible stages and test each gate

**First, establish a baseline and objectives.** Define the daily-user metric, instrument endpoint and database performance, record the real request mix and regional peaks, and set SLO, RTO, and RPO targets. Use production-like data and complete user journeys for load tests; test normal and peak traffic, bursts, sustained load, overload behavior, and recovery rather than benchmarking an isolated endpoint ([AWS Well-Architected, “Evaluate your workload performance”](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf05-bp02.html); [AWS Well-Architected, “Load test your workload”](https://docs.aws.amazon.com/wellarchitected/2023-10-03/framework/rel_adapt_to_changes_load_tested_adapt.html)). Test growth scenarios such as twofold, fivefold, and tenfold demand as planning cases, not forecasts; repeat tests after major query, schema, or architecture changes.

**Next, make production operation safe.** Put configuration and schema migrations under version control, use automated deployment and rollback, make application instances replaceable, secure database access, and automate backups. Restore a backup and record the actual recovery time before relying on the stated RPO/RTO. Use a managed multi-zone database or an equivalently operated deployment if it fits the startup’s budget and skills; managed infrastructure reduces some operational work but does not replace application-level testing and incident ownership ([Google Cloud, “Patterns for scalable and resilient apps”](https://docs.cloud.google.com/architecture/scalable-and-resilient-apps); [AWS Well-Architected, “Define recovery objectives”](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel13-bp01.html)).

**Then tune the measured bottleneck.** Profile slow queries, validate indexes and connection limits, and scale application instances horizontally. Add caching only with understood freshness and invalidation behavior. Add read replicas for demonstrated read pressure, and queues for independent work that can be delayed. Keep the team’s operational responsibilities explicit—application deployment, database recovery, security, incident response, and customer communication—even when the same people cover multiple roles.

For a database move, rehearse the process against a production-like copy. A migration can use a consistent initial load followed by transaction-log changes, then drain remaining changes and switch clients; if the allowed downtime is sufficient, quiescing writes and copying/restoring can be simpler. Validate the target before cutover and take a target backup. Once the target accepts new writes, a simple switchback can lose those writes unless reverse synchronization is designed and tested ([Google Cloud, “Database migration concepts and principles, Part 1”](https://docs.cloud.google.com/architecture/database-migration-concepts-principles-part-1); [Google Cloud, “Database migration concepts and principles, Part 2”](https://docs.cloud.google.com/architecture/database-migration-concepts-principles-part-2)). Use backward-compatible schema changes: add new structures, deploy compatible code, backfill in bounded batches, verify, switch traffic, and remove old structures only after rollback risk is understood. MySQL online DDL supports some changes but not all; rehearse the exact operation and version against representative data ([MySQL Reference Manual, “Online DDL Operations”](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)).

Finally, expand geography or data architecture only when real latency, availability, or legal requirements call for it. Forecast costs by region for application compute, database capacity, storage and I/O, backups, network egress, media/CDN, queues, and telemetry; autoscaling needs explicit limits and budget monitoring, and cross-region traffic can add cost ([Amazon RDS, “DB instance billing”](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/User_DBInstanceBilling.html); [Google Cloud, “Optimize resource usage”](https://docs.cloud.google.com/architecture/framework/cost-optimization/optimize-resource-usage)). Prefer managed services and a modest, actionable on-call and alerting system over premature adoption of sharding, active-active writes, a streaming platform, Kubernetes, or many microservices. No universal user-count threshold makes those technologies necessary.

## Conclusion

The immediate priority is not to reproduce a large social network’s architecture; it is to turn the current app into a measured, recoverable production service and prove its safe capacity with realistic tests. Keep the relational core and a simple deployment until data identifies the next bottleneck, while building the operational and security foundations that are difficult to retrofit.

A global audience calls for edge delivery, regional measurement, and careful data-governance decisions—not automatically a globally writable database. The startup should advance through explicit, tested decision gates, with each new layer justified by measured demand, user impact, legal requirements, or recovery commitments.
